## 2. 取材与合规：别人的东西哪些能用

结论先给：**代码能用（看许可证），JD 文本不能批量抓，功能创意随便参考。**

### 2.1 代码与开源项目

| 用法 | 能不能 | 条件 |
| --- | --- | --- |
| 引一个 MIT / Apache-2.0 / ISC 的库 | 能 | 保留版权声明；本仓库已有 unpdf、hono 等 |
| 读别人的开源实现找思路，自己重写 | 能 | 不构成复制；建议在 ADR 里写清「参考了谁的思路」 |
| 把别人的项目 fork / 换皮当参赛作品 | **不能** | 赛题红线：严禁直接使用已有开源项目包装参赛 |
| 抄一段 GPL / AGPL 代码进本仓库 | **不能** | 会把整个仓库变成 GPL，与 MIT 冲突 |
| 抄一段没写许可证的代码 | **不能** | 默认全保留版权，等于侵权 |

参考对象（只读思路，不拷代码）：ResumeForge（静态事实台账）、各类 JD 匹配工具、ATS 关键词工具。
共同点是「简历 → 关键词 → 打分」，我们要证明的恰好相反：**关键词匹配能告诉你缺什么词，
但只有对抗式追问能告诉你哪句话经不起问。**

### 2.2 JD 文本：BOSS 直聘这条路走不通，而且不该走

实测（2026-10-26）：`https://www.zhipin.com/robots.txt` 对通用爬虫写了 `Disallow: /*?*`，
而它的职位列表页全是带查询参数的 URL（`/web/geek/job?query=...&city=...`）。也就是说
**robots 协议下几乎没有可抓的职位页**。再加上用户协议普遍禁止批量抓取、平台有反爬与封禁机制，
公开仓库里放一个「BOSS 爬虫」会同时带来三个问题：法律风险、封号风险、评委观感。

所以本项目的取材口径是：

1. **模板 JD 由我们自己写**：原创文案，按行业分组，不抄任何平台的原文（D1 扩容走这条路）。
2. **用户自己的 JD 由用户上传**：他已经有权阅读的 JD，粘进产品里用，这是最干净的路。
3. **开放数据集要逐个核许可证**：CC BY-NC / ND 一律不用（商用与改作受限）；找不到明确许可证就当不能用。
4. **企业官网招聘页**：个别 robots 友好，但同样不做批量抓取——一次性的少量参考可以，不入库、不分发。

这条「有理有据地不做」，本身就是可复现性材料：评委能顺着 robots.txt 复核我们的判断。

## 3. D1 扩容：行业模板库怎么才够用

现在只有 6 个草稿种子（市场营销 / 财务会计 / 中小学教师 / 医护 / 公务员事业单位 / 人力资源）。
扩容目标：**12 个行业 × 每个行业 3 个具体岗位 = 36 个岗位模板**，每个模板包含

- `title`（岗位名，如「三甲医院 药房主管」）
- `jd`（180–260 字的原创 JD，写清职责 + 硬性要求 + 加分项）
- `resumeHints`（这个行业的人简历通常长什么样，用来给示例简历）
- `panel`（推荐的面试官组合：2 位预设 + 1 位该行业自建面试官草稿）

行业清单（拟）：医疗护理 / 教育教学 / 财务会计 / 人力资源 / 市场营销 / 供应链物流 /
建筑工程 / 机械制造 / 外贸翻译 / 行政文秘 / 法律合规 / 计算机软件。

界面上是「我是这个行业的」一排按钮 → 点一下把 JD、简历示例、面试官组合三处一起填好。
数据放 `packages/shared/src/templates.ts`（纯数据、可单测：每条都必须过 `interviewerDraftSchema` 与字数校验）。

## 4. 第二大功能：多 JD 驱动的岗位要求审阅

用户第 2 条的原话是「用户可以自己多上传一些 JD 让面试官阅览之后，面试官根据这些 JD 中的要求和
JD 所需的知识，审阅它的简历提出问题」。这不只是「多一个输入框」，它是**提问的驱动源换了**：

- 现在：提问由**简历里的主张**驱动（你说过什么，我就追问什么）。
- 加上之后：提问由**岗位要求**驱动（这个岗位要什么，你的简历有没有对上）。

### 4.1 数据流

```
多份 JD（1–8 份，粘贴 / 上传 .txt .md .docx .pdf）
  → 逐份抽要求：Requirement { id, text, anchor(JD 内区间), kind: 硬性|加分|职责, keywords }
  → 跨份聚类合并（同义要求归一，「熟悉 Java」与「Java 基础扎实」合成一条，记 sources: [jd1, jd2]）
  → 与简历主张对照：每条要求给 match：命中 / 弱命中 / 缺失
  → 追问阶段新增两类提问：
      · 命中但主张站不住 → 用要求原文加压（双锚点：简历区间 + JD 区间）
      · 弱命中 → 问边界（「要求 3 年经验，你这段是 1 年 8 个月，怎么算」）
  → 缺失清单单独成栏（不生成追问——简历里没有对应主张，问了也只是空转）
```

### 4.2 为什么它与现有内核是一致的（这点最重要）

锚定机制 `resolveAnchor(source, raw)` 本来就是「拿一段原文，在一份文本里找到逐字位置」，
**它不知道 source 是简历还是 JD**。所以 JD 锚点不需要新机制，只需要多传一个 source。
于是四个创新点全部延伸到新功能上：

- 证据锚定 → 提问带**双锚点**（简历片段 + JD 片段），两个都能点回原文
- 追问预算 → 仍然按主张记账，JD 驱动的问题也计入同一本账
- 意图契约 → 面试官契约里多一条「你依据 JD 的哪几条要求提问」
- 可复现回放 → JD 抽取与聚类也落卡带，无 Key 时整条链路照样跑通

### 4.3 落地代价（必须提前说清）

- schema 从 v5 升到 **v6**：新增 `jd` / `requirement` / `requirement_match` 三张表
- 新增两个编排阶段：`jd-extract`（逐份抽要求）、`jd-merge`（聚类合并）→ 演示卡带从 29 盘涨到 32 盘（实际只多了三个阶段各一盘）
- 前端新增一栏「岗位要求」，界面从四栏变五栏（要考虑 1600×1000 下的可读性）
- 提示词改动 → 全部卡带指纹失效 → 必须重跑 `npm run seed:demo`

## 5. 大功能清单：除了追问台，还能做什么

用户的意思是「把追问压力测试台当成一个大功能，还想做别的大功能」。下面是完整候选，按我的推荐分级。
**判断标准**：① 能不能复用现有内核（复用不了就是要重写一套）；② 演示 5–8 分钟里讲不讲得清；
③ 会不会摊薄「过程可复现」的证据密度。

### 第一梯队（建议做，与主线是同一棵树上的枝）

| # | 大功能 | 一句话 | 复用内核的部分 | 工作量 |
| --- | --- | --- | --- | --- |
| ① | **岗位要求审阅（JD 驱动）** | 多份 JD → 要求清单 → 简历逐条对照 → 带双锚点的追问 | Claim/Anchor/Probe/Budget/Contract/Replay 全部 | 15–20 h |
| ② | **成长档案（跨场次能力曲线）** | 同一份简历反复跑，看每条主张的判定怎么变、哪个类别总被打回 | Verdict 时间线 + C1 版本对比 + C2 仪表盘 | 10–14 h |
| ③ | **一岗一版简历生成** | 输入 JD，从通过质询的主张里挑出最相关的，生成针对该岗位的一版简历 | Claim + Suggestion + 采纳改写 + 导出 | 12–16 h |

②③ 与 ① 串起来是一条完整叙事：**先看这个岗位要什么（①）→ 再看你还差什么、怎么补（③）→
改完再跑一遍看进步（②）**。三句话讲完演示视频的主线，且每一句背后都是同一套 Claim/Verdict 数据。

### 第二梯队（可做，性价比取决于时间）

| # | 大功能 | 一句话 | 风险 |
| --- | --- | --- | --- |
| ④ | 复盘教练 / 答题卡 | 每一问一答回看，并生成「当场该怎么答」的口述稿 | 中：内容质量靠模型，离线难兜底 |
| ⑤ | 简历风险体检（不面试版） | 只跑锚定 + 判定 + 改写，30 秒出「哪句话经不起问」清单 | 低：几乎是把现有链路裁一半 |
| ⑥ | 行业知识追问包 | 按行业给一套标准追问（护理操作规范、会计准则…） | 中：要靠人工写题库，写少了像 demo |

### 第三梯队（本轮不做，写清理由）

| # | 大功能 | 为什么不做 |
| --- | --- | --- |
| ⑦ | 语音面试（TTS + 语音识别） | 破坏「无 Key 也能离线跑通」这个核心卖点；浏览器语音识别在离线回放里没有对应物 |
| ⑧ | HR 侧批量筛选 | 换了一个用户画像，与「帮求职者看清自己」的主线冲突；隐私与算力成本都高 |
| ⑨ | 账号体系 / 多人协作 | 赛题是个人作品，登录态会让「10 分钟复现」多一步 |
| ⑩ | 爬虫抓 JD | 见第 2.2 节，合规上不该做 |

### 我的建议

**做 ①②③，不做 ④–⑩。** 理由：①是用户明确要的；③是「一岗一版」这个最容易被评委理解的落点；
②是把「一次性体检」变成「长期跟踪」的唯一方式，而且它需要的 C1/C2 本来就在待办里。
四栏界面已经排得很满，再加两个大功能而不加新栏，是这一轮最大的设计约束。

## 7. 三个必须先说的硬约束

1. **技术文档 PDF 余量很薄**（当前 29 页，上限 30，余量 1 页；去掉强制分页后从 31 页降下来）。每加一个大功能都要顺手压一次排版，
   否则 `npm run docs:pdf` 会以退出码 1 失败。这一条会反复咬人。
2. **改提示词 = 全部卡带失效**。A1/A2/A4/B1/JD 驱动都要改提示词，每次改完必须
   `npm run seed:demo` 重录，并且 `npm run verify` 里的漂移门禁会拦住「忘了重录」。
3. **界面栏位已经满了**。四栏在 1600×1000 下刚好，JD 要求清单必须有地方放。
   候选：① 把「简历原文」栏做成左右分屏（左简历右 JD）；② 用抽屉/标签页；
   ③ JD 要求并进「主张与追问」栏做第二段。我倾向 ①，但它要重写中栏布局。

## 9. 协作方式（回应「我是小白，请多次审阅」）

每个大功能开工前，我先交一份**一页设计评审**：要解决谁的什么问题、怎么实现、有什么风险、
怎么验收（可执行的判断标准）。你只需要回答「做 / 不做 / 改哪里」，不点头我不写代码。
功能做完之后，我再交一份**验收报告**：门禁数字、截图、我自己找出的问题、以及我认为还不完美的地方。
这条规矩写进 AGENTS.md，成为后续所有迭代的默认流程。
