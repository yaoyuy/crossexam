# P11 设计评审：改与复用（B1 / B2 / C1 / C2 / C3）

> 按 AGENTS.md 第 7.1 条：开工前先给一页评审。本页写清「解决谁的什么问题 / 怎么做 / 风险 / 怎么验收」。
> 评审通过后动代码；越界改动重新评审。

## 一、这次要解决什么

用户（求职者）的闭环现在停在「跑完一场 → 勾选采纳 → 导出一版改完的简历」。还差五件事：

1. 改前改后只有一张清单，看不出「这句从什么变成了什么」（B2）
2. 改写口径只有一档：想要更保守或更大胆的人没有选择（B1）
3. 改完再跑一遍，两场结果互不关联，看不到「上次被追问的那三条，这次站住了」（C1）
4. 历史栏只有场次列表，没有趋势（C2）
5. 想把这一场发给别人看，得发四个文件（C3）

## 二、五项的做法与验收

### B2 逐条并排的改动对照（先做；不碰提示词、不碰数据库）

- **怎么做**：`packages/shared/src/revise.ts` 已有的 `applyRevisions` / `movedSpans` 之上加一个纯函数 `sideBySide(applied)`，
  按改写坐标把「改前一段 / 改后一段」切成对齐的成对段落；`packages/server/src/report.ts` 与 `report-html.ts` 的改动清单从列表变成两列；
  界面 `packages/web/src/components/RevisionBar.tsx` 加一个「并排看」开关，数据直接复用 `GET /api/sessions/:id/revisions` 的 `applied`。
- **风险**：低。不动提示词，卡带与指纹都不受影响。
- **怎么验收**：shared 单测 4 条（无改动 / 多条改动 / 重叠改动 / 坐标越界）；两种报告格式都能看到逐条对齐；e2e 断言开关切换后左右两栏都出现原文与改后。

### B1 改写风格档位：保守 / 常规 / 敢改

- **怎么做**：新建 `packages/shared/src/style.ts`（三档定义 + 中文标签 + 一句话说明 + 给提示词用的收敛程度片段），
  `packages/server/src/orchestrator/prompts.ts` 的 `SUGGEST_SYSTEM` 增加一节「这一版的收敛程度」；
  档位随会话落 `session.meta.style`（与 `difficulty` 同一套办法，不新增列）；投料台加三枚 chip；两份报告头部写明这一场用的档位。
- **硬边界不变**（这是本项的红线）：`newNumbersIn` 仍然拦简历里没有的数字，不许把「参与」写成「主导」，改前原文必须锚得回简历。
  档位只调措辞收敛程度，不调事实边界。
- **风险**：**suggest 阶段的卡带指纹全变**，必须重录；为了让离线演示三个档位都能跑，每档各录一套（4 盘 → 12 盘），卡带总数 48 → 56。
- **怎么验收**：脚本化客户端下三档各跑一场，断言提示词里出现对应档位、报告头部标注正确、契约指纹不受影响（档位不进契约）；
  门禁数字与卡带数量同步；e2e 断言建会话时档位落进 `session.meta`。

### C1 简历版本对比：同一份简历改完再跑一遍（旗舰项）

- **数据**：schema v10 给 `session` 加 `parent_session_id TEXT NULL`（自引用，不加外键约束：删掉父会话不该跟着删子会话）。
  链是**显式**的——用户在界面点「改完再跑一遍」时带上父会话 id，不靠简历 sha 去猜（采纳改写后简历原文必然变了，猜不出来）。
- **对齐**：新建 `packages/shared/src/compare.ts`，纯函数、不调模型：`alignClaims(prev, next, threshold)` 用字符二元组 Jaccard 相似度做一对一贪心匹配，
  产出 `{ pairs, added, removed }`；`verdictShift(prevVerdict, nextVerdict)` 给每条「变好 / 没变 / 变差」；再合成一块总结（判定分布变化、追问次数变化、从站不住变站得住的是哪几条）。
- **服务**：`GET /api/sessions/:id/compare` 返回与父会话的对比，没有父就是 `null`（界面说「这是第一版」）。
  建会话时 `POST /api/sessions` 接受可选 `parentSessionId`，校验它存在、且不构成环。
- **界面**：报告顶部一块「比上次」；采纳改写后出现「改完再跑一遍」按钮（自动带上父会话 id 与改完的简历文本）。
- **离线演示**：`npm run seed:demo` 跑两场——第二场的简历文本就是第一场采纳全部建议后的文本——让评委没有 API Key 也能看到对比。
- **风险**：相似度阈值是把双刃剑（阈值太高，所有主张都会被算成「新增」）。所以验收里必须有一条阈值敏感性用例；
  另外卡带会从 56 涨到约 100 盘。
- **怎么验收**：单测（完全相同 / 完全不同 / 改写后仍能对上 / 一对一不重复配对 / 阈值边界）；服务端一条端到端（跑两场后 `compare` 有数据、decode 出的判定变化与库里一致）；
  报告与界面各一块；e2e 真跑两场并断言「比上次」里的数字等于接口算出来的。

### C2 历史仪表盘

- **怎么做**：新建 `packages/shared/src/overview.ts`（纯聚合：场次数、判定分布合计、最常欠证据的类别、平均追问数、最近 5 场趋势点），
  `GET /api/sessions/overview` 读库后交给它算，历史栏顶部加一块；只在有 ≥2 场时显示趋势。
- **风险**：低，只读不改写。
- **怎么验收**：单测（空库 / 一场 / 多场 / 类别并列的稳定排序）+ e2e 断言界面数字等于接口值。

### C3 一场导出成可分享的单文件 HTML

- **怎么做**：`GET /api/sessions/:id/bundle.html`，把报告正文 + 时间线 + 简历原文 + 本版改动 + 反问串成一个**不引用任何外部资源**的 HTML（样式内联），
  `Content-Disposition: attachment`；界面右栏加「打包分享」按钮。
- **风险**：低。要守住一条：不许出现 `http://` / `https://` 外链（评委断网也要能打开）。
- **怎么验收**：服务端断言输出里没有外链、有 `<!doctype html>`、体积在合理区间；e2e 下载一次并检查头尾。

## 三、顺序与判断

**B2 → B1 → C1 → C2 → C3**。理由：先把不碰提示词与数据库的做掉（B2 最便宜、当天能验收）；
再做要重录卡带的（B1）；然后 C1——它要 schema v10、要跑两场演示，是这一阶段最重的一项；最后两个只读与导出。

## 四、两处默认选择（不同意就改）

1. **C1 的版本链是显式的**：用户点「改完再跑一遍」才连上；不做「按简历相似度自动认亲」。理由：自动认亲在简历被改过之后必然认错，
   而错认的后果是「比上次」里混进另一份简历的判定——这比没有对比更糟。
2. **离线演示为 C1 多跑一场**：卡带从 56 涨到约 100 盘，仓库体积增加约 1–2 MB。换来的是「没有 API Key 也能演示版本对比」这条主线。
