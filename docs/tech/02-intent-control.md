# 第二章　意图控制策略

赛题把 20% 的权重给了「方法创新性与意图控制」。这一章要回答的问题很具体：

> 当你有 3 个 Agent 在同一个沙盘里各自发挥时，**你凭什么说它们在你的意图之内行事？**

## 2.1 「在提示词里写要求」不是意图控制

大多数多 Agent 产品的控制手段是：在 System Prompt 里写一段要求，然后相信模型会遵守。
例如「每条提问最多追问 3 次」「你的提问必须来自简历原文」。

这在工程上是不成立的，理由是**提示词是建议，不是约束**：

| 你写的 | 模型实际可能做的 | 后果 |
| --- | --- | --- |
| 「最多追问 3 次」 | 第 4 次继续问 | 死循环，烧钱，演示卡死 |
| 「提问要来自简历原文」 | 编一段听起来像简历的话 | 幻觉式提问，用户被问懵 |
| 「一次只问一个问题」 | 问三个连在一起 | 用户不知道答哪个 |
| 「答不上来就停止追问」 | 继续换角度施压 | 用户被反复羞辱同一件事 |

更麻烦的是：**这些违规不会报错**。模型会返回格式完全合法的 JSON，
里面装着一条越界的提问；如果你只校验 JSON 结构，它会一路通过，直到用户看见。

所以 CrossExam 的设计原则是：

> **凡是可以被程序判定的约束，就不要交给模型自觉。**
> 模型负责「想出好问题」，程序负责「保证这个问题合规」。

## 2.2 四层意图控制：从声明到收敛

本项目把意图控制拆成四层，每层有明确的职责边界与失败表现。

| 层 | 名字 | 做什么 | 在哪实现 | 被拦下时用户看到什么 |
| --- | --- | --- | --- | --- |
| L1 声明 | 意图契约 Intent Contract | 每个 Agent 的 System Prompt 是结构化 JSON，可解释、可版本化、可 diff | `packages/shared/src/contract.ts` | 界面上可展开查看契约全文与指纹 |
| L2 校验 | 结构 + 锚定 | 模型输出必须过 zod schema；每条提问的引文必须能在简历里逐字定位 | `packages/shared/src/schemas.ts`、anchor.ts | 被拦下的提问列在「被拦下的追问」里，附原因 |
| L3 记账 | 追问预算 Probe Budget | 追问次数由代码记账，不是由模型数数 | `packages/shared/src/budget.ts` | 主张卡片上出现「已关停」与关停理由 |
| L4 收敛 | 判定与建议的代码级收敛 | 模型给的判定与建议还要过一遍确定性规则 | `packages/server/src/orchestrator/verdict.ts`、suggest.ts | 判定卡片上标注「这条判定不是模型直接给的」 |

这四层的顺序很重要：**先声明，再校验，再记账，最后收敛**。
每一层都只依赖上一层已经确定的产物，因此整条链路是确定性的、可单测的、可在离线模式下复现的。

## 2.3 L1 声明层：意图契约是数据，不是文案

### 2.3.1 结构

每个面试官 Agent 的行为由一个结构化对象完全决定，而不是一段散文式提示词：

```json
{
  "id": "tech",
  "version": 1,
  "persona": {
    "name": "技术面试官",
    "role": "tech",
    "seniority": "senior",
    "tone": "skeptical",
    "blurb": "资深工程师，冷静、只问细节"
  },
  "goal": "验证简历里的技术栈与项目描述是否真的出自本人之手，还是只写过 demo。",
  "tactics": [
    "追问技术选型的原因，而不是「用了什么」",
    "追问具体的失败与返工",
    "把简历里的一个数字拆开问口径"
  ],
  "constraints": [
    "每次提问必须携带能从简历里逐字找到的 quote",
    "引文至少 4 个字符",
    "一次只问一个问题",
    "只问简历里写过的东西，不要新造主张"
  ],
  "forbidden": [ ... ],
  "budget": {
    "maxRoundsPerClaim": 3,
    "maxProbesPerInterviewerPerClaim": 2,
    "maxTotalProbes": 60
  }
}
```

（以上为真实数据，来自 `PERSONA_PRESETS` 经 `buildContracts(['tech'], ...)` 生成，
技术面试官契约的指纹是 `042b385f925cf50f`，HR 是 `2375be34602e49f3`，业务主管是 `b2ed25a1d9d3995a`。）

### 2.3.2 为什么必须结构化

| 好处 | 具体表现 |
| --- | --- |
| 可解释 | 界面能把「它被允许做什么、被禁止做什么」摊开给人看，不用猜 |
| 可版本化 | `version` 字段 + 内容指纹，改一个字指纹就变 |
| 可 diff | 契约是 JSON，两次改动之间能看出改的是 tactics 还是 forbidden |
| 可对账 | 库里只存 `{id, version, digest}`，读侧按同样输入重算，指纹不一致就显示「契约已漂移」 |
| 可渲染 | System Prompt 由 `renderSystemPrompt(contract)` 确定性渲染，同样契约永远得到同一份提示词 |

第 4 条是本项目的一个明确取舍，也是设计上最值得讲的一处。

### 2.3.3 契约不落库全文，只落指纹

要做「契约可见」，最省事的做法是把契约 JSON 存进会话表，读出来显示。本项目没有这么做。

库里只存三样：

```
{ id: 'tech', version: 1, digest: '042b385f925cf50f' }
```

读侧每次按同样输入（面板 + 预算）**重新计算**契约全文，再用指纹与库里那一份对账：

```ts
const verified = match !== undefined
  && match.digest === digest
  && match.version === contract.version;
```

理由是「存副本」会把一句无法验证的断言混进产品：代码改了契约之后，老会话显示的仍是旧副本，
而旧副本已经不在任何地方运行了——**观众看到的和实际跑的不是同一份东西，且没有任何信号提示**。

重算 + 对账把这件事变成可判定的状态。界面上只有两种结论：

| 状态 | 界面文案 | 含义 |
| --- | --- | --- |
| 一致 | 与运行时一致 · 指纹 b2171c82 | 现在这份契约就是跑这一场时用的那份 |
| 漂移 | 契约已漂移 · 运行时 a1b2c3d4 → 现在 b2171c82 | 代码改过契约，这场会话用的是旧的 |
| 未开跑 | 尚未开跑 · 当前指纹 b2171c82 | 还没跑，无从对账 |

这个取舍的一般化结论写在 `findings.md` 的 F19 里：
**凡是「实现里有一份、展示里又抄一份」的数据，都该改成「一份真值 + 一个指纹」。**

### 2.3.4 契约的渲染：System Prompt 的六节结构

模型实际拿到的不是上面那段 JSON，而是由它确定性渲染出的六节提示词。以技术面试官为例（真实输出，界面截图 10-system-prompt.png 就是它）：

| 节 | 作用 | 是否可被程序校验 |
| --- | --- | --- |
| 你这一场的目标 | 告诉它「为什么问」 | 否（属于意图） |
| 可用手法 | 给出三条具体战术，避免泛泛而问 | 否 |
| 硬约束（由程序强制校验，违反的提问会被丢弃） | 四条必须满足的条件 | **是**（L2 锚定 + 去重） |
| 禁止 | 四条禁区 | 部分 |
| 追问预算（由程序记账，你不需要自己记） | 三条上限 | **是**（L3 记账） |
| 输出要求 | 精确的 JSON 形状 | **是**（zod） |

注意「硬约束」与「追问预算」两节的标题措辞：它们明确告诉模型「这件事由程序负责」。
这不是修辞——它减少了模型在边界上的试探，因为模型知道越界会被直接丢弃，而不是被商量。

## 2.4 L2 校验层：证据锚定，让提问可证伪

### 2.4.1 规则

每条提问必须携带一个 `quote`，它是**从简历里逐字复制的片段**。程序做三件事：

1. 先做逐字查找（`source.indexOf(quote)`），命中即 `exact: true`；
2. 失败则做归一化查找（全半角标点映射 + 空白折叠 + 小写），命中则 `exact: false`；
3. 两者都失败 → 这条提问被丢弃，理由写进「被拦下的追问」，**不消耗预算**。

锚点的坐标由程序用 `source.slice(start, end)` 算出来，**不采信模型给的 start/end**。
这条决定记在决策表 D7：模型给的偏移量只当提示，坐标以引文回原文重新定位为准。

### 2.4.2 四种拒绝理由

| 拒绝码 | 中文标签 | 触发条件 |
| --- | --- | --- |
| empty-quote | 引文为空 | 模型没给 quote |
| too-short | 引文太短 | 少于 4 个字符（短引文能在简历里命中任何地方，等于没锚定） |
| quote-not-found | 引文在简历里找不到 | 模型改写了原文、补了标点、或编了一句 |
| out-of-range | 区间越界 | 计算出的区间超出简历长度 |

### 2.4.3 为什么这条规则是全部创新点的地基

「提问必须锚定原文」把一句主观判断（这个面试官问得好不好）变成了一句客观判断（**这个问题有没有证据**）。
它带来三个连锁效果：

- **幻觉式提问被物理消灭**：模型编一句「你在某大厂做过高并发」是过不了锚定的，因为简历里没有这句话。
- **界面可以拒显**：没有锚点的提问不会进入事件日志，因此也不会进入界面。
- **追问变得可评估**：每条提问都指向一个具体的简历片段，因此「这条主张被问了几次、问到什么程度」是可统计的。

第三个效果直接引出下一层。

## 2.5 L3 记账层：追问预算，让死循环在设计上不成立

### 2.5.1 问题

多 Agent 追问最常见的失败形态是**不收敛**：A 问完 B 换个角度问，B 问完 A 再追一层，
每一轮都「还有可以问的」，于是永远停不下来。提示词里写「最多 3 次」拦不住它。

### 2.5.2 做法

把追问次数做成一个**不可变的账本**（`packages/shared/src/budget.ts`），每次提问前必须过闸门，通过才记账：

```ts
export interface BudgetConfig {
  maxRoundsPerClaim: number;              // 同一条主张全场最多追问几轮
  maxProbesPerInterviewerPerClaim: number; // 每位面试官对同一条主张最多问几次
  maxTotalProbes: number;                  // 全场追问总次数上限
  maxConsecutiveUnanswerable: number;      // 连续几次答不上来就关停这条主张
}

export const DEFAULT_BUDGET: BudgetConfig = {
  maxRoundsPerClaim: 3,
  maxProbesPerInterviewerPerClaim: 2,
  maxTotalProbes: 60,
  maxConsecutiveUnanswerable: 2,
};
```

闸门 `canProbe(state, claimId, interviewerId)` 按固定顺序做五道检查，**任何一道不过就拒绝，并给出可直接展示给用户的中文理由**：

| 顺序 | 检查 | 拒绝理由（原文） |
| --- | --- | --- |
| 1 | 主张是否存在 | 该主张不在本次沙盘中 |
| 2 | 主张是否已关停 | 关停理由，或「该主张已关停」 |
| 3 | 全场总次数 | 已达全场追问上限 60 次 |
| 4 | 该主张轮数 | 该主张已达追问轮数上限 3 轮 |
| 5 | 该面试官额度 | 该面试官对这条主张的提问额度已用完 |

顺序不是随意的：先判「这条主张还值不值得问」，再判「全场还有没有预算」，最后才判「这位面试官还有没有额度」。
这样拒绝理由总是最有信息量的那一条。

### 2.5.3 关停：连续答不上来就止损

账本还负责一件事：如果求职者连续 2 次答不上来同一条主张，这条主张被自动关停，理由写进账本：

> 已连续 2 次答不上来，继续追问没有信息增量

关停之后这条主张从「可追问清单」里消失（简历原文当然还是整份给模型），后续轮次不会再为它发起调用。
这条规则同时解决了两个问题：用户体验（不反复羞辱同一件事）与成本（不为已知结论烧 token）。

### 2.5.4 编排层的收尾条件

编排循环的条件是：

```ts
while (rounds < maxRounds && probeableClaims(budget, panel).length > 0) { ... }
```

这里有一个容易写错的地方值得写进文档：一开始用的是 `openClaims(budget).length > 0`，
而 `openClaims` 只表示「主张没有被 close」——额度用尽的主张仍然算 open，于是编排器会白烧一轮空的模型调用（live 模式是真金白银）。
为此新增了 `probeableClaims(state, interviewerIds)`：**存在至少一位面试官能通过 `canProbe` 的主张**。

另外，如果一轮下来所有面试官都没有提出任何新问题（都被去重闸门拦了），编排器直接收尾并写一条如实记录的提示：

> 第 3 轮没有任何新的追问，质询到此结束

这条提示会出现在报告里，也会出现在界面的事件日志里——**收敛是可见的，不是悄悄结束的**。

## 2.6 L4 收敛层：模型给的判定与建议，还要再过一遍代码

### 2.6.1 判定阶段的两条收敛规则

模型判完之后，`enforceVerdict` 会用两条确定性规则复核（`verdict.ts`）：

| 规则 | 条件 | 处理 | 理由文案 |
| --- | --- | --- | --- |
| 全没答上来还判「站得住」 | 有追问，所有追问的回答都无效，且模型判「站得住」 | 降级为「证据缺失」 | 候选人对这条主张的追问没能落出口径，原文这一句不足以判为「站得住」，按「证据缺失」处理 |
| 要证据却拿不出 | 判为「站得住」或「与原文矛盾」，但证据引文一条都定位不到 | 降级为「证据缺失」 | 模型判为「站得住」但模型拿不出可定位到简历原文的证据，按「证据缺失」处理 |

第二条尤其重要：**「站得住」是一个需要证据的结论**。模型想判 solid，就必须拿出能在简历里定位到的引文；
拿不出，这个判定就不成立。这与 L2 的锚定是同一个思想，只是从「提问」延伸到了「结论」。

第一条只做一件事：**防止过于乐观**，而不是替模型决定责任归属。代码手里只有一个布尔（这一场有没有答上来过），
而模型看得见每一轮问答——它比这个布尔更清楚该算「简历写得太笼统」（证据缺失，改简历就行），
还是「候选人自己拿不出东西」（无法回答，风险最高）。把「全体未答」一律改判「无法回答」的版本犯过一个真实错误：
模型的理由里明明白白写着「只有结论、没有口径，属证据缺失」，界面上却挂着「无法回答」的徽章——
理由是模型写的，结论是代码改的，两者当场矛盾（真实联网运行时才发现，见 5.6 第 5 条）。

为了让这两档可判别，`VERDICT_SYSTEM` 把判据写成了**责任在谁**：证据缺失 = 简历的错（这句话写得太笼统，
改法是把口径写进去）；无法回答 = 人的错（本人承认不记得、举不出例子、没做过，面试现场会直接翻车）。
拿不准时判「证据缺失」——它是一个可执行的结论，指向改简历；误判「无法回答」会让人以为这段经历该删掉。

被代码改过的判定会在界面上带一条琥珀色说明：「这条判定不是模型直接给的」+ 具体理由。
截图 06-verdicts.png 里的 C5 就是这种情况。

### 2.6.2 建议阶段的四道闸门

改写建议是最容易被模型「发挥」的环节——它会顺手帮你加一个更漂亮的数字。
因此 `suggest.ts` 设了四道闸门，任何一道不过，这条建议被拒绝并记录原因：

| 闸门 | 检查 | 拒绝理由 |
| --- | --- | --- |
| 是否需要建议 | 判定为「站得住」的主张直接跳过（不调用模型、不消耗预算） | 判定为「站得住」，不需要改写 |
| 改前原文可定位 | `before` 必须能在简历里锚定到 | 建议里的「改前原文」在简历中定位不到，无法应用 |
| 不许引入新事实 | `after` 里的数字必须是简历里已有的数字 | 建议里出现了简历原文中不存在的数字，属于新增事实 |
| 必须真的改 | `after` 不能为空，也不能等于 `before` | 建议改写后与原文相同，等于没改 |

第二道闸门的具体实现是 `newNumbersIn(after, resumeText)`：用正则 `/[0-9]+(?:\.[0-9]+)?/g` 抠出建议里的所有数字，
逐个检查是否在简历原文的数字集合里出现过；只要有一个新的，整条建议作废。

这条规则的效果可以在离线演示里直接看到：C2 的改写建议里出现的 `800` 与 `5000` 都来自简历原文，
模型没有机会把「QPS 5000」改成「QPS 8000」。

### 2.6.3 归属由调用方决定

建议的归属（这条建议属于哪条主张）**一律由调用方传入**，模型自报的 `claimId` 不看。
这一条在 live 实测里救过一次命：schema 曾把 `claimId` 列为必填，而提示词从没要求模型输出它，
于是 9 条建议全部因「claimId: Required」被拒；离线演示恰好写了这个字段，把矛盾完整掩盖。
修复后 `claimId` 改为 optional，并补了「模型不返回 claimId 也能出建议」的回归测试。

这个 bug 的教训写在 `findings.md` F23，也是本文档第 5.6 节要展开的「给模型输出造夹具的唯一真相是提示词里的输出要求」。

## 2.7 过程可视化：流式分片是观感，事件日志才是真相

赛题的 UX 评分项明确点名了「流式、思考可视化」。本项目的处理方式是一条明确的分界：

| | 流式分片 | 阶段事件 |
| --- | --- | --- |
| 内容 | 模型正在吐的字符 | 阶段开始 / 主张列表 / 追问列表 / 判定列表 |
| 落库 | **否** | 是（带 seq） |
| 可断线续传 | 否（刷新就没了） | 是（`?from=<seq>`） |
| 界面位置 | 卡片内的「正在作答」「正在定级」+ 过程面板的「实时输出」 | 阶段时间线 |

实现方式是给 LLM 客户端套一层 `withStreaming(inner, sink)`：各阶段的编排代码照旧 `await client.complete()`，
包装层把它改写成 `for await (inner.stream(req))`，把 `delta` 与 `reasoning` 分片送进 sink，最终结果取自 `done` 事件。
分片通过 SSE 的 `event: stream` 送出，**不带 id、不占 seq、不进事件表**。

理由写在 ADR-0004 里：分片每秒几十片，落库会让回放变慢、日志变吵，而分片拼出来的文本并不比 done 事件更可信。
**能断线续传的只有阶段事件——这是「可复现」与「好看」之间的一条明确分界。**

顺带一个工程细节：分片携带的 `channel` 字段（例如 `answer:P1`、`verdict:C3`）**刻意不参与卡带指纹**，
因为指纹只对请求做哈希（system / messages / temperature / maxTokens / json）。
这条设计让「加流式」这件事不需要重录任何一盘离线卡带。

### 2.7.1 思考分片：接上会思考的模型，界面上多一行斜体

思考（`reasoning`）与正文（`delta`）是两个独立通道，用分片上的 `kind` 区分；界面渲染成两行——
斜体那行是它正在「想」的，正下方那行是它要「说」的。要让这一行真的出现，需要三件事：

| 环节 | 做法 | 为什么 |
| --- | --- | --- |
| 选谁思考 | 装配层 `withStageModels(inner, routes)`，按 `req.purpose` 换模型 | 判定才需要「停下来想」；追问一轮十几次调用，全交给思考模型会把一场从十几秒拉成几分钟（ADR-0005） |
| 换模型不发卡带 | `LlmRequest.model` 与 `channel` 一样不参与指纹 | 已录好的 32 盘演示卡带不必重录 |
| 没有 Key 也看得见 | 合成脚本把 `reasoning` 写进卡带（同一个通道） | 离线演示也要能证明「思考可视化」是产品能力，不是联网才有的彩蛋；卡带 `model` 固定 `scripted-demo`，一眼可辨 |

实测（2026-10-26，示例简历，`CROSSEXAM_REASONING_MODEL=deepseek-reasoner` 只路由 verdict）：
一场得到 **2,355 片思考分片 / 8 路 `verdict:*` 通道**，账本 `reasoningTokens` 大于 0，同一场正文分片 5,814 片，两条通道都不进事件表。
一条要如实说明的代价：模型给的思考文本通常是**英文**（如 “The user asks: …”），这是模型侧行为，我们不翻译——硬翻译会让「思考」变成另一种编造。

## 2.8 本章要点

- 意图控制不是写提示词，是**四层可判定的机制**：声明（契约）→ 校验（锚定）→ 记账（预算）→ 收敛（规则）。
- 每条提问必须锚定简历原文，这是「提问可证伪」的地基，也是幻觉提问被物理消灭的原因。
- 追问预算由代码记账而非模型数数，因此死循环在**设计上**不成立，而不是「我们尽量避免了」。
- 判定与建议都要过代码复核：模型想判「站得住」必须拿出证据；想改简历不许引入新数字。
- 契约不落库全文，只落指纹，读侧重算对账——一份真值 + 一个指纹，胜过两份迟早不同步的副本。
