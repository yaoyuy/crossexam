# 第六章　局限、取舍与后续工作

一份技术文档如果只讲做成了什么，它的可信度反而更低。这一章写清楚：**什么没做、为什么没做、如果继续做会先做哪一件。**

## 6.1 已知局限

| # | 局限 | 影响 | 现状 |
| --- | --- | --- | --- |
| 1 | 求职者 Agent 只依据简历作答，不使用用户的真实记忆 | 它答不上来的问题，用户本人**可能**答得上来 | 这是刻意的：产品测的是「简历这句话本身能不能自证」，不是「你本人会不会」。报告里也如实写明这一点 |
| 2 | 判定区分度不足：真实模型下几乎全判「证据缺失」 | 用户看不到「表述过度 / 与原文矛盾 / 无法回答」这些信息量更大的档位 | 口径已从「全体未答一律改判」修正为「责任在谁」（见 2.6.1），但求职者 Agent 只依据简历作答，天然说不出「我不会」，所以「无法回答」稀少是结构性的 |
| 3 | 追问策略依赖单一模型的角色扮演 | 三位面试官的提问风格差异不如真人明显 | 契约层已把差异结构化（tactics / forbidden 各不相同），但同一模型扮演多个角色仍有同质化倾向 |
| 4 | 只支持中文简历 | 英文简历的锚定与切分未验证 | 锚定逻辑本身与语言无关，但 segment 的小节识别按中文标题写死 |
| 5 | 不做简历解析（PDF / DOCX） | 用户需要粘贴纯文本 | 有意为之：解析 PDF 会引入原生依赖与大量边界情况，与「10 分钟复现」冲突 |
| 6 | 单机单用户，无鉴权 | 不能直接部署到公网 | 产品定位是本地优先工具，简历属隐私数据，**不上传任何第三方存储** |

## 6.2 三个明确的取舍

### 6.2.1 抄一份文案，而不是拆包

web 不 import shared（因为 shared 经 util.ts 依赖 `node:crypto`），代价是判定标签与人设文案要抄一份。
正确的做法是把 shared 拆成零依赖 core + 带 IO 的 adapter，但那是一次全仓库重构。
本项目用**漂移测试**（`toBe` 断言同一个对象）替代重构，把风险压到「测试红了才发现」，而不是「重构期间功能停摆」。

### 6.2.2 合成卡带，而不是录真实模型输出

真实模型输出 + 真实简历 = 隐私泄漏，而卡带要提交进公开仓库。因此演示卡带是确定性脚本生成的，
并用三重痕迹标明它是合成的（model 字段、固定 recordedAt、估算 usage）。
代价是离线演示的追问质量不如真实模型（合成脚本只有 5 条主张，真实模型抽 8–10 条），
补偿手段是把真实实测的数字与追问原文写进本文档 5.5 节，让两者都能被核查。

### 6.2.3 分片不落库

流式分片走 SSE 但不进事件表，代价是刷新页面后看不到「刚才正在写的字」。
换来的是：回放不被几万条分片拖慢、日志不吵、且「能断线续传的只有阶段事件」这条边界非常清楚。
这条取舍记在 ADR-0004。

## 6.3 如果继续做，先做这五件

| 优先级 | 事项 | 为什么是它 |
| --- | --- | --- |
| 1 | 让候选人 Agent 能说「我不会」，而不只是「简历里没写」 | 根治 6.1 第 2 条的判定区分度问题：现在它只能引用简历，所以「无法回答」结构性稀少 |
| 2 | 追问阶段引入「用户补充事实」入口 | 用户被问住时能补一句真实情况，再判一次；这会把产品从「体检」变成「训练」 |
| 3 | 报告增加「按主张类别统计」 | 让用户看出自己是「数字类主张弱」还是「归属类主张弱」 |
| 4 | 支持英文简历 | 锚定逻辑已与语言无关，只需放宽 segment 的小节识别 |
| 5 | 把 shared 拆成 core + adapter | 消除抄文案的技术债 |

## 6.4 结语

这个项目想做的一件事，用一句话说就是：

> **在简历投出去之前，先让三位不同的面试官把它拆一遍，并且告诉你哪一句你答不上来。**

技术上它试了三件不太常见的事：

1. **把「提问必须有证据」做成程序闸门**，而不是提示词里的请求——这让幻觉式提问在物理上无法进入系统；
2. **把「追问次数」做成不可变账本**，而不是模型自己数数——这让死循环在设计上不成立；
3. **把「过程证据」做成会话日志的自动产物**，而不是事后整理的文档——这让 120 余次提交、9 份 Prompt 链快照与本文档里每一个数字都可追溯。

第三件事也是这个项目对赛题「过程可复现性」这条 25% 权重最直接的回答：
过程不是我事后描述的，是仓库里一条命令就能重新导出的。
