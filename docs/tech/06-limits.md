# 第六章　局限、取舍与后续工作

一份技术文档如果只讲做成了什么，它的可信度反而更低。这一章写清楚：**什么没做、为什么没做、如果继续做会先做哪一件。**

## 6.1 已知局限

| # | 局限 | 影响 | 现状 |
| --- | --- | --- | --- |
| 1 | 求职者 Agent 只依据简历作答，不使用用户的真实记忆 | 它答不上来的问题，用户本人**可能**答得上来 | 刻意如此：测的是「简历这句话能不能自证」，不是「你本人会不会」；报告里也写明 |
| 2 | 判定区分度不足：真实模型下几乎全判「证据缺失」 | 看不到「表述过度 / 与原文矛盾 / 无法回答」这些信息量更大的档位 | 口径已修正为「责任在谁」（见 2.6.1）；但求职者 Agent 只依据简历作答、天然说不出「我不会」，所以「无法回答」稀少是结构性的 |
| 3 | 追问策略依赖单一模型的角色扮演 | 三位面试官的提问风格差异不如真人明显 | 契约层已把差异结构化（tactics / forbidden 各不相同），但同一模型扮演多个角色仍有同质化倾向 |
| 4 | 只支持中文简历 | 英文简历的锚定与切分未验证 | 锚定逻辑本身与语言无关，但 segment 的小节识别按中文标题写死 |
| 5 | 当初判断「解析 PDF 会引入原生依赖」，与「10 分钟复现」冲突 | 一度只能粘贴纯文本 | ✅ 已推翻：纯 JS 的 `unpdf` 出现后这条不再成立，现支持 PDF / Word / 文本导入，字节不落盘（ADR-0007） |
| 6 | 单机单用户，无鉴权 | 不能直接部署到公网 | 产品定位是本地优先工具，简历属隐私数据，**不上传任何第三方存储** |

## 6.2 三个明确的取舍

### 6.2.1 抄一份文案，而不是拆包

web 不 import shared（shared 经 util.ts 依赖 `node:crypto`），代价是判定标签与人设文案要抄一份。正确做法是把 shared 拆成零依赖 core + 带 IO 的 adapter，但那是一次全仓库重构；本项目用**漂移测试**（`toBe` 断言同一个对象）替代，把风险压到「测试红了才发现」，而不是「重构期间功能停摆」。

### 6.2.2 合成卡带，而不是录真实模型输出

真实模型输出 + 真实简历 = 隐私泄漏，而卡带要提交进公开仓库。因此演示卡带由确定性脚本生成，
并用三重痕迹标明是合成的（model 字段、固定 recordedAt、估算 usage）。
代价是离线追问质量不如真实模型（合成脚本 5 条主张，真实模型抽 8–10 条）；补偿是把真实实测的数字与追问原文写进 5.5 节，两者都能被核查。

### 6.2.3 分片不落库

流式分片走 SSE 但不进事件表，代价是刷新后看不到「刚才正在写的字」；换来回放不被几万条分片拖慢、日志不吵，
而且「能断线续传的只有阶段事件」这条边界很清楚（ADR-0004）。

## 6.3 如果继续做，先做这三件

| 优先级 | 事项 | 为什么是它 |
| --- | --- | --- |
| 1 | 让候选人 Agent 能说「我不会」，而不只是「简历里没写」 | 根治 6.1 第 2 条的判定区分度问题：现在它只能引用简历，所以「无法回答」结构性稀少 |
| 2 | 支持英文简历 | 锚定逻辑已与语言无关，只需放宽 segment 的小节识别 |
| 3 | 把 shared 拆成 core + adapter | 消除抄文案的技术债 |

原表里的另外两件——追问阶段可补一句事实、报告按主张类别统计——已在 P10 落地（见 3.6.10）。

这张表是「技术上最先该补的」；「产品上还能加什么」见 [候选功能清单](../feature-candidates.md)——已落成的按阶段与 ADR 列出，还没做的三条（真 .docx / 英文简历 / 无障碍键盘）连同「为什么不做」的判断一起留档。

## 6.4 结语

这个项目想做的一件事，用一句话说就是：

> **在简历投出去之前，先让三位不同的面试官把它拆一遍，并且告诉你哪一句你答不上来。**

技术上它试了三件不太常见的事：

1. **把「提问必须有证据」做成程序闸门**（不是提示词里的请求）——幻觉式提问在物理上进不来；
2. **把「追问次数」做成不可变账本**（不是模型自己数数）——死循环在设计上不成立；
3. **把「过程证据」做成会话日志的自动产物**（不是事后整理的文档）——330 余次提交、66 份 Prompt 链快照与本文档里每个数字都可追溯。

第三件事也是对赛题「过程可复现性」那条 25% 权重最直接的回答：过程不是事后描述的，是仓库里一条命令就能重新导出的。
