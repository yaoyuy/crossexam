## 5.2 三条最有说服力的测试

### 5.2.1 直播与历史必须给出同一个界面

`packages/web/test/state.test.ts` 把同一串 15 个事件喂给两条路径：

```
路径 A：sandboxReducer + {type:'event'}       （模拟 SSE 直播）
路径 B：stateFromHistory(events)              （模拟刷新后从库里读）
断言：claims / probes / budget / errors / interviewers / rejectedClaims / eventCount 完全一致
     只有 phase 不同（'running' vs 'done'）
```

这条测试守的是产品承诺「刷新后看到的和刚才实时看到的是同一场」。它一共有 17 条断言，
其中还覆盖了：预算事件让主张关停、作答报错在卡片上显示、空追问轮自己补提示、未知 claimId 与重复 probeId 被丢弃、致命错误把 phase 置为 failed。

### 5.2.2 提示词必须是确定性的

`packages/server/test/orchestrator-extract.test.ts` 有一条：

```
同一个输入渲染两次提示词 → 逐字节相同
```

理由不是洁癖：卡带按**提示词指纹**寻址，提示词抖一字节，整盘离线回放就失效。
因此所有阶段的提示词全部是纯函数，不含时间戳、不含随机数、不依赖 `Object.keys` 的顺序。

### 5.2.3 锚定不采信模型给的坐标

同文件另一条：给模型一个**错误的 start/end**，但引文是对的，
断言最终锚点是程序用 `indexOf` 重新定位出来的区间。
这条把「证据锚定」从一句口号变成了可验证的行为。

## 5.5 真实模型实测（DeepSeek，live 模式）

这一节的意义是：**证明离线演示不是靠卡带撑起来的空壳**，接上真模型确实能跑。

### 5.5.1 端到端结果

| 项 | 值 |
| --- | --- |
| 模型 | deepseek-chat（OpenAI 兼容协议） |
| 一场耗时 | 20.0 s |
| 主张 / 追问 / 轮数 / 建议 | 10 / 18 / 3 / 9 |
| token | 输入 47,941 · 输出 8,355 · 缓存命中 7,424 |
| 判定 | 10 条「证据缺失」（判定口径调整后的实测，见 5.6 第 5 条） |
| 被锚定机制拦下的主张 | 0（真实模型的引文质量比预期好） |

### 5.5.2 真实追问的质量抽样

下面这条是真实模型对「首屏加载从 2.4s 降到 0.8s」的追问，未经任何修改：

> 2.4s 和 0.8s 这两个首屏加载数字是怎么测出来的——用什么工具、在什么网络条件和设备上、取的是几次采样的什么统计口径？

求职者 Agent 的回答（同样未经修改）：

> 这个……简历里只写了「首屏加载从 2.4s 降到 0.8s」这个结果，具体用什么工具测的、什么网络条件和设备、采样几次取什么统计口径，简历里没有写，我这边没法给你具体细节。

**这一问一答就是整个产品的价值主张**：它不是「AI 帮你写简历」，而是「AI 找出你答不上来的那句」。

### 5.5.3 真实模型的流式分片

live 模式下的一场实测：**5,814 个分片 / 29 路 channel / 0 片进入事件表 / 21 条阶段事件**。
接上思考模型（`CROSSEXAM_REASONING_MODEL=deepseek-reasoner`，只路由 verdict）之后再测一场：
**2,355 片思考分片 / 8 路 `verdict:*` 通道 / 账本 `reasoningTokens` > 0 / 整场 22.7 s**——
思考与正文分走两个 `kind`，但同样不进事件表。
这组数字同时证明了三件事：流式真的在流、分片确实被隔离在事件日志之外、阶段事件的规模稳定在二十条左右。

### 5.5.4 两条诚实的观察（不是结论）

| 观察 | 说明 |
| --- | --- |
| 真实模型抽的主张比合成脚本多 | 361 字简历抽 8–10 条，合成脚本固定 5 条；真实模型还会把「2023.06 - 2025.03」这类时间线也抽成主张 |
| 判定口径调完之后，「无法回答」几乎不再出现 | 求职者 Agent 只依据简历作答，它天然说不出「我不会」，所以「无法回答」本就该是少数；数字类主张更容易落在「证据缺失」（简历没写口径，改简历即可）。代价是区分度下降：这一场 10 条判定全是「证据缺失」 |

## 5.6 五个在实测中抓到的真 Bug

下面五个 bug 都不是设计阶段发现的，是**真跑起来才暴露**的。它们比任何架构图都更能说明这套工程是真的在运转。

| 序号 | 现象 | 根因 | 为什么之前没抓到 |
| --- | --- | --- | --- |
| 1 | 真实模型下 9 条修改建议全部失败 | schema 要求 `claimId` 必填，提示词从未要求输出它 | 合成卡带恰好写了这个字段，把矛盾完整掩盖 |
