# 第一章　问题定义：简历里那句话，你答不上来

## 1.1 一个具体的失败场景

求职者张明（本文档全程使用的示例人物）简历上写着两句话：

> 主导重构订单系统，首屏加载从 2.4s 降到 0.8s。
> 主导引入 Redis 缓存，QPS 从 800 提升到 5000。

他投出去，进了面试。面试官问：「2.4s 到 0.8s，怎么测的？取的均值还是 P75？样本量多少？」

张明答不上来。他确实做过这个优化，但那个数字是同事报给他的；他没测过，也不记得口径。
于是面试官得到两个结论：这个人对数字不负责；这份简历不可信。

**问题不在于他会不会写代码，而在于简历上的每一个数字，都是一个等待被追问的主张，而他没在被追问之前演练过。**

这个场景有三个关键性质，直接决定了产品形态：

| 性质 | 含义 | 对产品的约束 |
| --- | --- | --- |
| 主张是可枚举的 | 一份简历能抽出 5–12 条「可被追问的主张」 | 不需要做通用对话，做「逐条质询」就够 |
| 追问是有方向的 | 面试官不会随机问，他们拆口径、拆归属、拆因果 | 追问策略可以被写成可复用的意图契约 |
| 反馈必须可执行 | 「你答得不好」没有价值，有价值的是「这句话改成什么」 | 输出必须回落到简历原文的具体片段 |

## 1.2 现有方案为什么不够

市面上的简历工具分三类，各自缺一块：

| 类型 | 代表 | 它能做什么 | 它不能做什么 |
| --- | --- | --- | --- |
| 简历生成 / 美化 | 各类在线简历编辑器 | 排版、模板、导出 | 不检验内容是否站得住 |
| AI 润色 | 通用大模型对话 | 把句子写得更好看 | 会替你编，且编得比原文更自信 |
| 模拟面试 | 题库式 / 通用 AI 面试官 | 出题、打分、给建议 | 不锚定你的简历原文，问题与你写的东西无关 |

第三类是最近的形态，也是本项目的近邻。它的核心缺陷可以用一句话说清：
**它的提问不携带证据。** 面试官问「谈谈你最有挑战的项目」，这句话对任何人成立，
因此它对任何人都不成立——它无法指出你简历里哪一句话站不住。

## 1.3 CrossExam 的解法：把「面试」变成「逐条主张的证据审计」

CrossExam 的输入是**一份简历 + 一份目标岗位 JD**，输出是**每条主张的判定 + 回落到原文的修改建议**。
中间的过程是 3–5 位人设不同的 AI 面试官，对每条主张并发追问。

一场完整的质询有五个阶段，全部由程序编排、全部可回放：

```
简历 + JD
   │
   ├─ ① 抽取主张  extract   从简历里抽出可被追问的主张，每条必须携带逐字引文
   │                        锚不到原文的主张当场丢弃（不是降级，是丢弃）
   │
   ├─ ② 并发追问  probe     3 位面试官按各自的意图契约同时提问
   │                        每轮：预算闸门 → 锚定闸门 → 去重闸门
   │
   ├─ ③ 求职者作答 answer   求职者 Agent 只能引用简历原文作答，编造的引文被丢弃
   │                        连续答不上来 → 该主张自动关停（不再浪费追问）
   │
   ├─ ④ 判定      verdict   每条主张给出：站得住 / 表述过度 / 证据缺失 / 与原文矛盾 / 无法回答
   │                        两条代码级收敛：全没答上来 → 无法回答；要证据却拿不出 → 证据缺失
   │
   └─ ⑤ 改写建议  suggest   把「答不上来」翻译成「这句话该怎么改」
                            四道闸门：改前原文必须定位得到、不许引入新数字、不许等于原文
```

五种判定不是设计出来的修辞，而是**证据审计的五个可能结论**：

| 判定 | 含义 | 触发条件（产品语义） |
| --- | --- | --- |
| 站得住 | 主张有原文支撑，且追问下给出了可核验的口径 | 答得上 + 能援引原文 |
| 表述过度 | 主张本身没错，但说法超出了证据能支撑的范围 | 答得上但暴露了口径不一致 |
| 证据缺失 | 主张可能成立，但拿不出任何可定位到简历的证据 | 模型判 solid/contradicts 却给不出引文 → 代码降级 |
| 与原文矛盾 | 追问下的回答与简历原文冲突 | 回答援引的原文与主张指向的事实相反 |
| 无法回答 | 所有追问都没答上来 | 代码强制：有追问且全部无效回答 |

## 1.4 与近邻产品的差异（不是形态差异，是判断依据的差异）

赛题明确禁止「直接使用已有开源项目包装参赛」，因此这里做的是**能力对照**而不是功能对照。
本项目在立项时研究过一个成熟的同类产品（本地优先的 AI 求职工作台，Apache-2.0，545 次提交，7 个主模块），
它把「防编造」做在了**生成侧**：维护一份用户核实过的事实台账，只有核实过的事实才允许进入生成。

| 维度 | 事实台账式（生成侧防编造） | CrossExam（质询侧做压力测试） |
| --- | --- | --- |
| 触发时机 | 写简历之前 | 简历写完之后、投出去之前 |
| 核心动作 | 拦截：不许写没核实过的事实 | 质询：写下的话经不经得起追问 |
| 输出物 | 一份更安全的简历 | 一份带判定与改写建议的审计报告 |
| 对模型的要求 | 不许发挥 | 必须发挥（扮演不同面试官施压） |
| 失败模式 | 台账太严，简历写不出来 | 追问太空，等于没问 |

两者的关系是互补而不是重叠：台账保证「写下来的都是真的」，
质询保证「写下来的都答得上」。本项目选择后者，因为它有一个前者没有的性质：
**追问是可以被证伪的**——一次提问如果锚不到简历原文，它就是一个可以被程序判定为无效的提问。
这条性质是第二章全部意图控制手段的起点。

## 1.5 谁会用、用在什么时候

| 用户 | 场景 | 得到的价值 |
| --- | --- | --- |
| 应届生 / 转行者 | 简历投出去石沉大海，不知道问题在哪 | 在投递前发现「这句我答不上来」 |
| 有经验但久未面试的人 | 项目是两年前做的，细节忘了 | 被追问后知道该补哪段记忆、该改哪句话 |
| 简历辅导 / 就业指导老师 | 批量看学生简历 | 一份可下载的审计报告，指出具体句子 |
| 面试教练 / 训练营 | 做模拟面试 | 用不同人设反复施压，且过程可复现 |

它不是「AI 帮你写简历」，而是「AI 帮你找出简历里最脆的那一句」。
这个定位带来一个直接的产品约束：**报告必须定位到字**。
「你的项目描述不够具体」是无效反馈；「第 81–108 字这句『首屏加载从 2.4s 降到 0.8s』答不出测量口径，建议改为……」才是有效反馈。

## 1.6 本章要点

- 问题是「简历上的数字经不经得起追问」，不是「简历写得好不好看」。
- 因此产品形态是逐条主张的质询，不是通用对话。
- 因此每条提问必须携带简历原文锚点——这是可证伪性的来源。
- 因此输出必须回落到原文的具体片段——这是实用价值的来源。
