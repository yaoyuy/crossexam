# 第四章　可复现性论证

赛题 25% 给「过程可复现性与演进链路」。这一章不讲愿景，只回答三个可核查的问题：

1. **别人能不能在我的机器之外跑起来？**（4.1–4.3）
2. **没有 API Key 能不能看到完整效果？**（4.4）
3. **我凭什么说这些提交是真做的，而不是最后一次性倒进去的？**（4.5–4.6）

## 4.1 复现路径：四条命令

```
git clone <仓库地址>
cd crossexam
npm install
npm run preview
```

然后打开 http://127.0.0.1:8787 ，点「一键示例」，点「开始质询」。

| 步骤 | 需要什么 | 不需要什么 |
| --- | --- | --- |
| clone | 网络 | 不需要账号（公开仓库） |
| install | Node ≥ 22.6（实测 24.14.0）、npm | 不需要 pnpm / yarn、不需要编译工具链 |
| preview | 磁盘可写 | 不需要 Docker、不需要 API Key、不需要数据库服务 |
| 浏览器操作 | 任意现代浏览器 | 不需要装任何客户端 |

### 4.1.1 实测耗时（干净目录，`npm run repro` 的输出）

| 步骤 | 耗时 | 说明 |
| --- | --- | --- |
| git clone | 4.0 s | 含 29 盘卡带与 10 张截图 |
| npm install | 14.4 s | 116 个包，来自 npmmirror |
| npm run verify | 13.1 s | 类型检查 + 313 条断言 + 冒烟 + 构建 |
| 起服 + 跑完一场 + 下载报告 | 0.4 s | 回放模式，21 ms 跑完整场 |
| **合计** | **33.9 s** | 距 10 分钟上限有 17 倍余量 |

这个表不是估的，是 `tools/repro/repro-check.mjs` 在一个**全新临时目录里 git clone 出来**的仓库上逐步计时得到的。
同一台机器多次预演落在 34–40 秒之间（`clone` 受磁盘缓存冷热影响最大），这张表记的是最近一次完整预演。
写文档时的第一条原则是：**复现耗时必须是实测数据，且必须由命令生成，不能手写**（决策 D16）。

## 4.2 为什么没有原生依赖

| 依赖 | 选择 | 如果换成常见的替代品会怎样 |
| --- | --- | --- |
| 数据库 | `node:sqlite`（Node 内置） | better-sqlite3 需要 node-gyp + Python + VS Build Tools，Windows 上失败率极高 |
| 服务端框架 | Hono（纯 JS，零依赖链） | Express 也行，但 Hono 自带 `streamSSE` 且体积小 |
| 校验 | zod（纯 JS） | — |
| .env 载入 | `process.loadEnvFile`（Node ≥ 20.12 内置） | dotenv 会多一个包，且本项目只需要一行 |
| 浏览器驱动 | 系统 Edge/Chrome + CDP + Node 全局 WebSocket | Playwright 会下载 200 MB 浏览器 |
| 文档渲染 | 自写 md2html（零依赖） | pandoc 需要单独安装 |
| 截图 | CDP `Page.captureScreenshot` | — |

上表每一行都能对应到 `AGENTS.md` 第 6 节那条约束：「引入需要本地编译的原生依赖会毁掉 10 分钟复现，需要 ADR 才能破例」。
至今没有破例。

## 4.3 三个「静默失败」的坑，以及它们如何变成规则

可复现性的敌人往往不是「跑不起来」，而是「**看起来跑起来了，其实用的是别的东西**」。本项目踩过三个：

| 坑 | 现象 | 变成的规则 |
| --- | --- | --- |
| 说明书写了 `cp .env.example .env`，程序从没读过它 | 填了 `CROSSEXAM_MODE=live` 仍是回放，配置静默失效 | 启动横幅必须打印「已载入哪个 .env」或「没有 .env」 |
| 端口上挂着旧进程 | live 实测报「0 分片」，其实测的是流式功能落地**之前**的旧服务 | 一次性实测起服务前必须自检端口为空，并核对写入的是自己的临时库 |
| 通用 .gitignore 模板的 `bin/` 段 | 源码被静默忽略，P0 提交漏掉了导出器 CLI | 忽略规则要**正反各测一遍**：密钥被挡住 + 源码没被挡住 |

第二、三条的完整复盘在 `findings.md` F22 与 F6/F10。它们共享同一个教训：

> **退出码为 0 不代表事情办成了。凡是「静默忽略」的机制，都要在事后做一次正面确认。**

## 4.4 离线回放：没有 Key 也能看到完整效果

### 4.4.1 卡带机制

回放模式下，每一次模型调用的「问题」被哈希成一个 24 位指纹，**答案**就存在以该指纹命名的 JSON 文件里：

```
fixtures/llm/
├── 0a3f...c2.json    extract 阶段的回答
├── 1b7e...d9.json    probe 阶段某位面试官的回答
└── ...               共 29 盘
```

指纹只对请求的五项内容做哈希（system / messages / temperature / maxTokens / json），
因此**改了提示词，指纹就变，旧卡带自然失效并响亮报错**。这既是一个约束，也是一道门禁（4.4.3）。

### 4.4.2 29 盘卡带覆盖了什么

| 阶段 | 卡带数 | 说明 |
| --- | --- | --- |
| extract | 1 | 抽主张 |
| probe | 9 | 3 位面试官 × 3 轮 |
| answer | 10 | 10 条追问各一次作答 |
| verdict | 5 | 5 条主张各一次判定 |
| suggest | 4 | 4 条需要改写的建议（「站得住」的那条跳过） |

跑完一场离线演示的权威数字（`.tmp/doc-stats.mts` 直接调 `runAndPersist` 实测）：

| 指标 | 值 |
| --- | --- |
| 耗时 | 21 ms |
| 轮数 / 主张 / 追问 / 判定 / 建议 | 3 / 5 / 10 / 5 / 4 |
| 被锚定机制拦下的主张 | 1 |
| 判定分布 | 站得住 1 · 表述过度 1 · 证据缺失 2 · 无法回答 1 |
| token | 输入 21,266 · 输出 2,267 |
| 每位面试官追问数 | tech 4 · hr 3 · hiring_manager 3 |

### 4.4.3 卡带是合成的，而且必须被证明是合成的

这 29 盘卡带由 `createDemoScriptedClient` 用**确定性脚本**生成，不是真实模型的输出。这一点在文档里、在 `fixtures/README.md` 里都写明，并且有三重可核查的痕迹：

| 痕迹 | 怎么核查 |
| --- | --- |
| 每盘卡带的 `model` 字段都是 `scripted-demo` | 打开任意一个 JSON 就能看到 |
| `recordedAt` 是固定常量 `2026-10-26T00:00:00.000Z` | 因此重跑 `npm run seed:demo` **逐字节相同**，git status 干净 |
| usage 是按字符数折半的估算值，不是计费数据 | 生成器里有明确注释 |

为什么必须这么做？因为**卡带是要提交进公开仓库的**。真实模型输出 + 真实简历 = 隐私泄漏。
因此 `fixtures/README.md` 里写了一条红线：只允许用示例简历录制卡带。

### 4.4.4 提示词漂移门禁

卡带最大的风险是「代码改了提示词，卡带没重录，演示静默变味」。守住它的是一条测试：

```
packages/server/test/demo-cassette.test.ts
  用仓库里已提交的 fixtures/llm 起一个真实 app，
  POST /api/sessions（useDemo）→ POST /run?stream=0
  断言：200 / 主张 5 / 被拦 1 / 判定含 unanswerable 与 solid / 建议 ≥ 1
```

这条测试跑的是**已提交的素材**，因此任何人改了提示词而忘了 `npm run seed:demo`，提交门禁立刻变红。
它同时也是一份「离线演示确实能跑完」的回归证据。

### 4.4.5 想联网跑真模型怎么办

```
cp .env.example .env       # 填 LLM_BASE_URL / LLM_API_KEY / LLM_MODEL
# .env 里设 CROSSEXAM_MODE=live
npm run start
```

服务启动横幅会明确打印当前模式与「是否已载入 .env」。实测在 DeepSeek 上跑通（见 5.5 节）。

## 4.5 演进链路：120 余次提交是怎么来的

### 4.5.1 规则写在仓库里

`AGENTS.md` 第 2 节把赛题的提交要求变成了可执行的工程规则：

| 规则 | 内容 |
| --- | --- |
| 粒度 | 一个提交 = 一个可独立说明的改动。禁止 `git add -A && git commit` 式大杂烩 |
| 判据 | 提交前先问：**这个提交对应哪一次 AI 对话？** 答不上来就说明粒度不对 |
| 格式 | Conventional Commits + 中文简述（不超过 50 字）+ 正文写「为什么这么改」 |
| 署名 | **禁止** `Co-Authored-By` 等 AI 署名尾注（GitHub 会把它们解析成账号并计入贡献者列表） |

### 4.5.2 阶段与提交的对应

| 阶段 | 内容 | 提交数（约） |
| --- | --- | --- |
| P0 | 仓库初始化、工程约定、DSH 会话导出器 | 5 |
| P1 | 领域内核：锚定 / 切分 / 预算 / 契约 / schema；LLM 适配层 | 17 |
| P2 | 五阶段编排、存储、HTTP/SSE、报告、示例简历、冒烟 | 15 |
| P3 | 前端：包骨架、HTTP 契约、事件折叠、三栏界面、单端口托管 | 7 |
| P4 | 截图器、意图契约可见、复现预演、README 复现指南、流式吐字 | 30+ |
| P5 | 技术文档、Prompt 链刷新、发布清单 | 进行中 |

### 4.5.3 一个具体例子：一次 Bug 修复对应哪一次对话

以「修改建议全部失败」这个 bug 为例，它对应的提交链是：

```
c8a6e90 fix(shared): 修改建议不再要求模型自报主张编号
```

提交正文写的是「为什么」：提示词从未要求模型输出 claimId，而 schema 把它列为必填；
合成卡带恰好写了这个字段，于是离线全绿、真实模型全红。这类信息只有写进提交正文才留得下来。

## 4.6 Prompt 链：过程证据不是事后补写的

赛题要求提交「≥3 个核心功能迭代的完整 Prompt 链（提问、AI 建议、如何引导修 Bug）」。

本项目的做法是**从第一行代码起自动导出**：

| 环节 | 实现 |
| --- | --- |
| 原始数据 | DSH 把每一次会话写成 zstd 多帧压缩的 JSONL，落在 `%APPDATA%\dsh-desktop\harness\sessions\<工作区>\<会话>\session.v4.jsonl.zstd` |
| 解析 | `tools/dsh-export` 逐帧解压（`zstdDecompressSync` 只解第一帧，必须扫描魔数 `28 B5 2F FD`），按 turn 组织成时间线 |
| 脱敏 | 自动识别 6 类密钥格式（OpenAI / Anthropic / GitHub / AWS / Bearer / KEY=value 赋值），命中即替换 |
| 过滤 | 只把 `source.kind === 'user'` 的消息当真人提问，系统注入（runtime-context / skill-catalog / plugin:hindsight / time-context / agent-instructions）全部丢弃 |
| 分页 | 超过 40 万字符自动按**条目**边界切分（不是按轮次，因为单轮可能 144 万字符），每份都能在网页上直接渲染 |
| 产物 | `docs/prompt-chain/` 下 9 份分片，共 2.7 MB，覆盖整个开发过程 |

这条链带来三个别的方式给不了的性质：

| 性质 | 含义 |
| --- | --- |
| 不可事后美化 | 快照是会话日志的直接产物，改一个字就会和日志对不上 |
| 包含失败 | 走错的路、被推翻的方案、修 bug 的过程都在里面，不是只挑成功的展示 |
| 可复跑 | `npm run export:prompt` 一条命令重新生成，不需要手工整理 |

## 4.7 本章要点

- 复现路径四条命令，33.9 秒（实测，由 `npm run repro` 生成），17 倍余量。
- 零原生依赖是硬约束，至今没有破例。
- 离线回放让「没有 Key 也能看到完整效果」成立，29 盘合成卡带 + 一条漂移门禁守着它。
- 提交粒度规则写在仓库里，120 余次提交每一次都能对应到一次具体的开发动作。
- Prompt 链是会话日志的直接产物，自动导出、自动脱敏、自动分页——过程证据不是作文。
