# ADR-0018：版本对比按文本相似度配对，不另存一份「档案」

- 状态：已采纳（2026-10-27，P11 的 C1）
- 相关：决策 D54、发现 F67、`packages/shared/src/compare.ts`、`packages/server/src/compare.ts`、`packages/shared/src/compare.ts` 的 `alignClaims`

## 背景

「改完再跑一遍，判定怎么变」是这份产品最该回答的问题，也是它区别于一次性简历体检的地方。
要回答它，必须先解决一个没有现成答案的问题：**两场会话的主张怎么配成对**。

主张没有稳定标识。每场会话都从 C1 重新编号（这是刻意的，见 F 系列关于 id 的结论），
而用户采纳改写之后，被改的那一句在原文里已经不存在了——文本变了，id 也变了，
两个都不适合拿来当配对依据。

## 决策

1. **按主张文本的相似度配对**，不引入外部标识：`packages/shared/src/compare.ts` 的
   `alignClaims(prev, next, threshold = DEFAULT_ALIGN_THRESHOLD)` 用 bigram Jaccard 相似度
   全对打分，按分数降序贪心一对一，剩下没配上的进 `added` / `removed`。
   `DEFAULT_ALIGN_THRESHOLD = 0.34` 是拿真实简历试出来的：换说法落在 0.45–0.65，
   同主语不同事约 0.2，毫不相干约 0。
2. **配对结果按「这一场」的顺序重排**，不按上一场。报告是新简历的读法，从上往下读，
   每一条旁边说一下它上次是什么；按上一场排会让读者反复回跳。
3. **只存一条版本链，不存「档案」表**。`session.parent_session_id`（schema v10）记「这一版是从哪一场改出来的」，
   对比时现算。刻意**不加外键**：删掉上一版不该把这一版带走，此时接口回 `parentMissing` 一档，
   界面说「上一版不在了」，而不是假装这是第一版。
4. **判定位移复用短板排序**：`verdictShift` 用 `shortfall.ts` 的 `WEAKNESS_RANK`
   （solid 0 / overstated 1 / unsupported 2 / contradicts 3 / unanswerable 4）比大小，
   任一为 `null` 记 `unjudged`。**不新写一套「好坏」判断**——报告里的短板排序和版本对比
   必须对同一件事给出同一个答案（与 D47 同族）。
5. **结论只算一次**：`compareHeadline` 那一句话由 shared 产出，Markdown 报告、可打印 HTML、
   界面「比上次」栏三处读同一份。

## 取舍

- 相似度配对会错配。两份完全不同的简历里出现两句「负责订单系统」，它们会被配成一对。
  代价换来的好处是不需要用户维护任何档案，也不需要模型参与配对（配对是纯函数，可测试、可复现）。
  如果以后要更准，正确的方向是让锚点区间参与打分，而不是让模型来配——那会让同一份数据每跑一次结论都不同。
- 只谈「变好 / 没变 / 变差」而不给分数。分数（相似度 0.41）对读者没有意义，
  有意义的是「这一条上次是表述过度，这次站得住了」。
- 版本链刻意不做环检测：父会话 id 在建档那一刻由服务端新生成，环在结构上长不出来；
  真正的失败模式是父会话被删，单独成一档。
- 代价：离线演示必须跑两场，卡带 56 → 149 盘（三档强度 × 三档风格 × 两场）。
  换来的是「没有 API Key 也能看见判定变好」——否则这条主线在评委手里只剩文档里的一句话。
