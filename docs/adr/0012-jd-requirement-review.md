# ADR-0012：岗位要求对照——读 JD 三次调用，追问挂第二处锚点

- 状态：已采纳
- 日期：2026-10-27
- 相关：ADR-0002（离线卡带按提示词指纹寻址）、`packages/shared/src/requirements.ts`、`packages/server/src/orchestrator/jd.ts`、`packages/server/src/orchestrator/probe.ts`、`docs/roadmap-v2.md`

## 背景

用户在 m07544 第 2 条说：「用户可以自己多上传一些 JD 让面试官阅览之后，面试官根据这些 JD 中的要求和 jd 所需的知识，审阅它的简历提出问题」。

这条要求把产品从「简历自身的压力测试」推进到「简历与岗位的对照」。它带来三个必须先定的问题：

1. **要调几次模型**。JD 可能有多份、要求可能几十条、主张十几条；最直白的做法是「每条要求 × 每条主张」逐对问一次，
   那是一场几百次调用。而卡带按**提示词指纹**寻址（ADR-0002）：调用次数膨胀的直接后果是离线演示的卡带从 32 盘变成上百盘，
   而且提示词一改，全部失效。
2. **「简历里没写」算不算问题**。如果把缺失的要求也派给面试官去问，面试官就会去质问一件简历里根本没提的事，
   那不是在压力测试，那是在念岗位说明书。
3. **第二处锚点怎么来**。第 1 条创新点是「提问必须携带简历原文的字符区间」，现在追问还要同时挂一段 JD 原文，
   需不需要新机制？

## 决策

1. **三段链路，各自只调一次（逐份抽要求那次按份数并发）**：
   `jd-extract` 逐份 JD 并发抽要求（每份一次调用，上限 12 条，锚不到原文的当场丢弃）；
   `jd-merge` 一次把所有 JD 的要求归并（同一件事写在两份 JD 里算一条，`sources` 记来源，代表锚点取引文最长的那一份）；
   `jd-match` 一次把全部要求与全部主张摆在一起逐条对照，给出「答得上 / 答得含糊 / 简历里没写」。
   1–8 份 JD 因此是 3–10 次调用，卡带 29 → 32 盘。
2. **「简历里没写」单独成栏，不生成追问**：它只作为对照结果与报告里的一节呈现。面试官该追的是简历里说了但站不住的话。
3. **双锚点复用同一个 `resolveAnchor`**：`resolveAnchor(source, raw)` 从一开始就不关心 `source` 是简历还是 JD，
   所以「一条追问同时挂简历片段与 JD 片段」只是再调一次同一个函数——双锚点与单锚点一样可验证、可回放。
   `requirementId` 与 `jdQuote` **要么都给，要么都不给**；要求原文锚不回 JD 时退回普通追问并在 rationale 里说明，
   宁可少一个锚，不编一个锚。
4. **空 JD 合法**：没有 JD 时整条链路跳过，面试官照各自的契约追问。`jdProblems([])` 返回空数组——
   把「至少要有一份 JD」做成接口错误，纯简历场次就整条路走不通；「还没上传」是界面的提醒，不是数据校验的错。
5. **对照结果落三张表，双锚点落 `probe` 的五个新列**：`jd` / `requirement` / `requirement_match`（都带 `session_id` 级联），
   以及 schema v7 给 `probe` 补的 `requirement_id` / `jd_quote` / `jd_start` / `jd_end` / `jd_exact`。
   最后这五个列不是设计时想到的，是**重开一场历史会话时双锚点消失了**才发现的。

## 后果

- 好处：追问第一次有了「外部依据」——不是面试官觉得该问，而是这份岗位要求写着，且要求原文可定位到 JD 的第几个字。
- 好处：产品从「简历写得好不好」扩展到「简历与这个岗位对不对得上」，同时没有引入任何新的锚定机制（复用内核）。
- 好处：界面上「答得上 / 答得含糊 / 简历里没写」三组就是一份可直接用于投递前自检的清单，缺失的那组不需要跑模型就能看懂。
- 代价：提示词多了一个阶段设置，**改任意一个 JD 阶段的提示词都要重录全部卡带**（这是 ADR-0002 的既有代价，不是新增的）。
- 代价：schema 到 v7，`probe` 表重建一次；迁移测试用「手搓一个 v6 的最小库再迁移」守住老库能读回。
- 代价：界面从四栏变五栏（右栏做简历 / JD 分屏）。这是在 roadmap 第 8 节里请用户拍板过的取舍。
