# ADR-0013：补充说明就是零宽插入——复用采纳改写通道，坐标不落库

- 状态：已采纳
- 日期：2026-10-27
- 相关：ADR-0009（采纳改写只收主张 id、集合重算）、`packages/shared/src/supplement.ts`、`packages/shared/src/revise.ts`、`packages/server/src/revisions.ts`

## 背景

P10 的 A1 是「让求职者补一句真话」：面试官把某条主张判成证据缺失之后，用户可能确实做过这件事，只是简历里没写。
补的这句话要能落进最终简历，否则用户还得自己手工复制粘贴——那「自动改简历」就断在半路上。

三个必须先定的问题：

1. **它在简历里是什么形态**。它没有对应的原句，所以不是替换。
2. **它落在哪一行**。简历是纯文本、没有结构，插入位置只能由那条主张的锚点算出来。
3. **坐标要不要落库**。如果落库，用户改了简历、或者锚点变了，坐标就失效了。

## 决策

1. **插入是区间的特例，不是第二种操作**。`Revision` 允许 `start === end` 且 `before` 为空串，表示「在这一行的行尾加一行」。
   采纳链路的入口、事务、撤销、报告渲染全部复用已有的那一套，不为插入新开一条通道。
2. **坐标在采纳时由锚点现算**。`insertionPointAfter(resumeText, anchor)` 取锚点结尾所在行的行尾（CRLF 时插在 CR 之前）。
   `supplement` 表只存那句话本身（`session_id` / `claim_id` / `text` / `digest`），**不存坐标**——原文没变时坐标可复算，原文变了旧坐标本来也不该用。
3. **一条主张允许两条改动**。`revision` 表主键从 `(session_id, claim_id)` 换成 `(session_id, ordinal)`（schema v8），
   否则「既补一行、又改一句」时第二条会覆盖第一条。
4. **补一句真话不等于改原文**。补充说明在报告里单独成节「你补的证据」，并写明这几句是用户自己写的事实、
   简历原文没有被改动、采纳之后才会作为新的一行加在对应主张下面。采纳之前它只是候选项之一，和其它建议一起勾选、一起确认。
5. **零宽插入不占最右边界**。`applyRevisions` 的重叠检测对插入不推进 `lastEnd`：
   落在同一位置上的「一插入、一替换」互不重叠，都该落地。（这条是门禁抓出来的，见 F60。）

## 后果

- 好处：补的证据和模型的改写走同一条路——同一个勾选框、同一次确认、同一份导出，用户不需要理解两种操作的区别。
- 好处：不存坐标就没有「坐标过期」这一类 Bug；撤销也天然幂等（集合重算，见 ADR-0009）。
- 好处：报告里「模型建议改什么」与「你自己补了什么」分得清，后者不会被误读成模型编的。
- 代价：schema v8 一次表重建迁移；`revision` 主键换掉是本次最贵的一处改动。
- 代价：界面上一张建议卡可能同时出现「改写建议」与「补一句真话」两块，用户要自己决定勾哪个（默认都不勾）。
