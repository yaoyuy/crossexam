# ADR-0010：零门槛入口是「双击一个脚本」，不是打包成 exe

- 状态：已采纳
- 日期：2026-10-26
- 相关：`tools/launcher/`、`启动.cmd`、`启动.sh`、`装个快捷方式.cmd`、AGENTS.md 第 6 节

## 背景

用户第 7 条要求（m04531）：「最好做得完全没用过计算机的人都能直接安装迅速用起来。」
第 10 条要求：「安装后经用户允许自动创建桌面快捷方式。」

对一个 Node 项目来说，「别人能用」通常有三种做法：

1. 打包成单文件 exe / 安装包（pkg、nexe、Electron Builder 一类）；
2. 交给用户自己敲命令；
3. 提供一个双击就能跑的脚本，把该判断的都判断好。

第 1 种和第 2 种在这个项目里都不成立：

- 打包工具链本身就要**本地编译**（下载预编译二进制、拼 node 运行时、处理 `.node` 原生模块），
  直接撞上 AGENTS.md 第 6 节「引入需要本地编译的原生依赖会毁掉十分钟复现」。更现实的问题是：
  我自己这台机器上打包成功，不代表评委的机器上双击不报毒、不被 SmartScreen 拦住。
- 第 2 种与「完全没用过计算机的人也能用」直接矛盾。README 里的四条命令对开发者是常识，对其他人是门槛。

## 决策

1. **入口是两个脚本，不是二进制**：Windows 是 `启动.cmd`，macOS / Linux 是 `启动.sh`。
   脚本只做三件事：`where node` 查一下（查不到就打印下载地址并停下）、`cd` 到仓库根、把活交给 `tools/launcher/launch.mjs`。
2. **判断逻辑全部抽成纯函数**（`tools/launcher/src/plan.mjs`，零 IO）：版本解析、版本比较、该走几步、
   快捷方式脚本长什么样、三个平台怎么开浏览器。`launch.mjs` 只负责碰文件和起进程。
   于是「第一次该装依赖、第二次不该」这种逻辑可以被单测守住（12 条），而不是靠人肉点两遍。
3. **不猜、不替用户装**：Node 太旧就直说需要 22.5 以上并给出下载页，不尝试静默升级；
   `parseNodeVersion('24.14')` 返回 `null` 而不是补一个 0——认不出就说不认识。
4. **幂等**：已经装好依赖、已经构建过就跳过；端口上已有一个实例在跑，就不再起第二个，
   直接把浏览器叫到前面并打印「已经有一个质询室在 8787 端口上跑着，直接打开浏览器」。
5. **桌面快捷方式指向启动脚本，不指向 node 本体**：以后改启动方式不用重建图标；
   只有真的给了图标路径才写 `IconLocation`——写空字符串会让快捷方式在桌面上显示成一张白纸。
6. **快捷方式必须由用户主动触发**：`装个快捷方式.cmd` 是独立入口，`启动.cmd` 不会顺手往桌面丢东西。
   自动化测试用 `CROSSEXAM_LAUNCH_NO_BROWSER=1` 跳过开浏览器，不给测试留「悄悄弹窗」的口子。

## 后果

- 好处：「装了 Node → 双击 → 浏览器自己打开」这条路径上没有一个需要理解的概念；
  第一次约 20 秒（装依赖 + 构建），之后约 2 秒；全部判断都有测试，不靠人工复述经验。
- 好处：跨平台只多一个 `.sh`，不引入任何打包产物，仓库里没有二进制文件，`git clone` 的体积不变。
- 代价：用户仍然要自己装一次 Node（这是整个技术栈的前提，无法绕开）。启动器能做的是把「装哪个、装完怎么办」讲清楚。
- 代价：`.cmd` 在少数被策略锁定的机器上可能被拦。因此 README 保留命令行那条路，两条路都能到同一个界面。
