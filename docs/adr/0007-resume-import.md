# ADR-0007：简历导入自己拆包，不引入会破坏「10 分钟复现」的解析栈

- 状态：已采纳
- 日期：2026-10-26
- 相关：ADR-0001（服务端零构建）、ADR-0004（离线回放）

## 背景

用户提出「支持 doc 和 pdf 导入简历」（m04531 第 2 项）。看着是一件小事，实际上它把
产品的入口从「你得会复制粘贴」变成「选一个文件」，而这一项的门槛决定了非计算机专业的
用户能不能用起来。难点全在**解析**：一份简历可能是 PDF（文字版或扫描件）、.docx、
老版 .doc、纯文本。

这里有一条不能破的约束：评委要在 10 分钟内把整条链路跑起来。任何需要本地编译的
原生依赖、或任何体积巨大且带可选原生模块的库，都会把这条承诺变成赌博。

## 决策

1. **PDF 用 unpdf。** 它是纯 JS、零依赖（内联了自己裁剪过的 pdf.js 构建），
   npm 安装即用，不需要任何本地编译。对比过的 pdfjs-dist 有 34.9 MB，
   而且带着可选原生依赖 @napi-rs/canvas。取文字只需要 extractText，unpdf 正好够。
2. **.docx 自己拆。** docx 就是一个 zip：node:zlib 的 inflateRawSync 解出
   word/document.xml，再按段落标签取文本，零依赖、几十行。为一个自己就能做的事
   引入一个库，等于白送一个复现失败点。
3. **老版 .doc 明确拒绝，并告诉用户怎么办。** 二进制 .doc 的解析要读 FIB、分片表、
   还可能带压缩文本流；试过的 word-extractor 解析质量不稳定，而本机根本造不出可信的
   测试样本——没有样本的代码就是没验证过的代码。于是卸载它，改成返回 415 与一句
   「用 Word / WPS 打开后另存为 .docx 再导入」。
4. **文本导入先 UTF-8、再试 GBK，取乱码少的那个。** 中文用户手里真的会有 GBK 的 txt；
   「解码失败」比「猜一次」更糟。
5. **上传的字节不落库、不留盘。** 解析完只留文本进 SQLite（和粘贴进去的简历待遇完全一致），
   buffer 用完即弃。隐私口径与技术文档里的说法必须与代码一致。
6. **错误分档，给不同的 HTTP 码。** 太大 413、格式不支持（含老版 doc）415、
   解析不出内容（扫描件、空文件、损坏）422。界面上就直接是中文原因，不是「导入失败」。

## 备选方案

- **pdfjs-dist 直接上**：功能最全（能取坐标），但 34.9 MB + 可选原生依赖，被约束否决。
- **mammoth / docx 解析库**：只为了取纯文本而引入一个带样式映射的解析器，不值。
- **交给浏览器端解析**：界面能少写一点，但解析逻辑就进不了 Node 测试，也无法在
  没有界面的情况下验证；而且「上传的字节不出本机」这条会更难说清。

## 代价与边界

- 扫描件（图片型 PDF）读不出文字是**预期行为**，返回 422 并明说「这看起来是扫描件，
  没有文字层」。这是如实报告，不是 bug。
- 复杂版式（多栏、表格、文本框）取出来的文字顺序可能不完美；本产品的用途是
  「拿它当质询的材料」，不是还原排版。
- unpdf 的 extractText 会把传入的 Uint8Array 底层 buffer 转移走（pdf.js worker 语义），
  同一个 buffer 不能喂第二次。测试里每次现造字节。（见 findings F39）

## 验证方式

- packages/server/test/import.test.ts：11 条断言覆盖扩展名与魔数分派、docx 逐字取文、
  PDF 取文、扫描件走 pdf-no-text、损坏文件、GBK 中文、空文件、超大文件分档。
- packages/server/test/http.test.ts：4 条接口断言（200 两类 + 415 两类 + 422 + 400）。
- packages/web/test 与 tools/ui-e2e/e2e.mjs：界面上「从文件导入」真选一份文件、
  解析结果落进输入框、并写明文件类型与字数（e2e 用页面内 DataTransfer 造 File，
  不依赖 CDP 的 DOM.setFileInputFiles）。
