# ADR-0021：轨迹是在相邻两版之间连出来的，不跨版配对

- 状态：已采纳（2026-10-27，P12 的 ②）
- 相关：决策 D57、发现 F73/F74、`packages/shared/src/growth.ts`、`packages/server/src/growth.ts`

## 背景

C1 的「比上次」只回答相邻两版：「这一版比上一版好了没有」。可用户改到第三版、第四版时，
真正想知道的是**这条我改了几回、现在还站不住吗**。三版以上就成了链上的轨迹问题。

数据面已经齐了：`session.parent_session_id`（schema v10）把每一版串成链，
每场的主张与判定都在库里。缺的只是「把链读出来、把配对串起来」。

## 决策

1. **只在相邻两版之间配对，再把配对串起来。** 复用 `compare.ts` 的 `alignClaims`
   （bigram Jaccard，阈值 0.34）。不跨版直接配对：跨越三版算一次相似度，阈值的作用被放大三次，
   而配错的后果在界面上**没有任何办法被看出来**——一条真实轨迹被算成「消失 + 新增」两条，
   或者两条不同的轨迹被并成一条。相邻配对每步只错一次，而且能指出错在哪一步。
2. **`persistent` 的口径写死四个条件**：最新一版仍在 && 出现过 ≥ 2 版 && 一次都没站住 && 判定非空。
   四条分别挡掉四种误报：改完站住的、只出现一版的、中途消失的、还没判的。
   少任何一条，面板上的「改了还在被打回」都会开始说谎。
3. **链是读 `parent_session_id` 连出来的，不是新表。** 版本链只在建档那一次写入（父 id 由服务端生成），
   结构上长不出环；真正的风险是**父会话被删**——v10 故意没给这一列加外键（删上一版不该把这一版带走）。
   所以沿链往上走撞到空要单独成 `broken` / `brokenAt` 一档，界面上说清「再往前那一场已经被删掉了」，
   而不是假装这是第一版。
4. **窗口上限 `GROWTH_MAX_VERSIONS = 12`。** 再往回看，主张早就改得不像同一句，连出来的轨迹是噪声；
   也不做分页——这个视图是「回看一眼」，不是档案库。
5. **追问数取不到就是 `null`，不猜 0**（与 ADR-0019 同一条纪律）。
6. **界面做成覆盖层，不做第五栏。** 四栏在 1600 宽下刚好；成长档案是偶尔回看一次，不是常驻视角。
   打开才读库：它不像「比上次」每次跑完都该有。
7. **轨迹排序写死**：`persistent` 优先 → 版本数降序 → 最新版号降序 → key 升序。
   同一批输入永远同一个顺序，测试与截图才可比。

## 取舍

- **不做「跨版直接配对」**：省下的是一次遍历，赔上的是配错的可见性。
- **不做「一条主张一个总相似度」的聚类**：那会把「改到完全不像」的两条合并成一条，
  而它恰恰是最值得看见的变化——改到不像，等于这条主张被重组了。
- **不给成长档案做导出**：报告里的「比上次」已经承担了对外的那部分；轨迹是自查用的。
- **不把窗口做成无限**：链越长，单次读库的查询越多（每版要读主张与追问），12 版之外的信息密度已经很低。

## 与前面几条的关系

这条 ADR 是 C1（ADR-0018）的延长线：C1 回答「相邻两版」，成长档案回答「整条链」。
两者共用同一个配对函数与同一套判定位移口径，所以「比上次说变好 4 条」与
「轨迹里 4 条已经改站住」是同一个数——这正是 D47/F27/F69 那条纪律要的东西。
