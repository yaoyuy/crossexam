# ADR-0019：历史仪表盘只做聚合，不引入新判定

- 状态：已采纳（2026-10-27，P11 的 C2）
- 相关：决策 D55、发现 F69/F70、`packages/shared/src/overview.ts`、`packages/server/src/overview.ts`、`packages/web/src/overview.ts`

## 背景

历史栏原本只是「一列场次」。跑到第三场之后，这一列就失效了：用户看不出自己是在变好还是在打转，
而「变没变好」恰恰是这份产品最该回答的问题（与 C1 同一个动机，只是 C1 比两场、C2 比很多场）。

难点不在界面，在于**「这些数字由谁算」**。报告里已经有「站得住 N 条」、短板里已经有「最该补的类别」，
如果仪表盘自己再算一遍，两处迟早会对同一份数据给出不同的数字——这不是崩溃，是更难查的那种失败（F27 / D47 同族）。

## 决策

1. **聚合是一个纯函数，在 shared 里**：`packages/shared/src/overview.ts` 的 `overviewOf(sessions: SessionFacts[])`。
   它只接收数据、不读库、不调模型、不看时间，因此可以被单测钉死，也能被报告或其它界面复用。
   服务端 `packages/server/src/overview.ts` 只做一件事：读库把 `SessionFacts` 攒出来，交给它。
2. **判定分布与类别短板一律复用现成实现**：`verdictCounts`（`compare.ts`）与 `categoryShortfalls`（`shortfall.ts`）。
   **不新写第二套「哪个判定更差」的排序**。仪表盘说「最集中的是技能掌握」，报告里那一条就必须也是技能掌握。
3. **追问数取不到就是 `null`，不猜 0**：`SessionFacts.probes` 允许为 `null`，`meanOf` 只在非 `null` 的场次上求平均。
   猜 0 会让「还没跑完的场次」把平均值往下拽，而界面没有任何办法把这件事说出来。
4. **窗口上限 200 场，且这是性能边界不是分页**：`OVERVIEW_WINDOW = 200`。
   不设上限的话，跑到几百场之后每次打开页面都要把每一场的主张与追问各读一遍。
   接口照样收 `?limit=`，但界面上没有「翻页」——仪表盘回答的是「最近这一阵子怎么样」。
5. **趋势不足两场就不画**：`trendLine` 在少于两个点时返回 `null`，界面上整块趋势不出现，
   换一句「只跑了 N 场，趋势要等第二场跑完才看得出来。」而不是画一根孤零零的柱子假装有趋势。
   趋势点**时间升序**（`ordered.slice(0, TREND_POINTS).reverse()`），柱状图从左到右就是时间往前走。
6. **空库也要给人话**：`overviewSessions` 从不返回 `null`，空库时 headline 是「还没有跑过任何一场。」。
   但**界面上整块不渲染**（`facts.empty` 时 `OverviewBar` 返回 `null`）——新用户第一眼该看投料台，不是一排空柱子。
   这是刻意的分工：数据层永远有结论，界面层决定什么时候值得说。
7. **顺手把「同一份简历跑过几场」算出来**（`resumeGroups` / `sameResumeRuns`，按 `resumeHash` 分组）。
   它是 P12 成长档案的接口：只有当同一份简历被跑过多次，跨场次的比较才有意义。
   现在只用它出一句提示，不因为「这个数据现在没大用」就不算——事后补字段会让旧场次缺数据。

## 取舍

- **不做时间维度以外的筛选**（按岗位、按难度、按风格分开统计）。
  分桶会让每个桶里的场次少到没有统计意义，而且「我换了难度所以变差了」这种结论不该由仪表盘替用户下。
  需要细看时，历史列表和每场的报告都还在。
- **不给「进步了多少分」这样的单一数字**。判定是五档离散值，压成一个分数要编造权重；
  现在给的是「已判 X 条里站得住 Y 条，还欠 W 条」，读者自己能判断。
- **趋势只画已判与站得住两根柱**，不画欠证据、不画追问数。一根柱能说清一件事，四根柱就没人看了；
  追问数放在每根柱的 `title` 里，鼠标停上去才出现。
- 代价：`overview` 每刷新一次会话列表就要把 200 场的主张与追问读一遍。
  这是可接受的：界面只在建会话、跑完一场、删一场时刷新；真到几百场之后再考虑缓存，现在加缓存是过早优化。
