# ADR-0004：流式分片是过程观感，不进事件日志

- 状态：已采纳（2026-10-26）
- 相关：ADR-0003（单端口演示）、packages/server/src/llm/streaming.ts、packages/web/src/state.ts

## 背景

赛题的用户体验一项明确点名「流式、思考可视化」。这个项目的一次会话要打 20–40 次模型调用，
每次都能吐出几百到上千个分片（实测一场 5814 片）；而事件日志（event 表）同时承担两个职责：

1. 前端断线续传的游标：SSE 的 `id` 就是事件 seq，重连能接着收；
2. 会话过程的唯一真相：Markdown 报告、历史重放、统计都读它。

## 决策

1. 五个阶段照旧 `await client.complete()`，一个字都不改。流式是**客户端包装**
   （llm/streaming.ts 的 `withStreaming(inner, sink)`）：把 `inner.stream()` 的分片按 channel 外推，
   最终结果仍取自 done 事件——**绝不用分片拼一个「看起来差不多」的文本**给下游过 zod 与锚定。
2. 分片走 SSE 的 `event: stream`，**不带 id、不写事件表、不落库**；
   阶段事件（stage / claims / probes / answers / budget / verdicts / suggestions）照旧带 seq，是唯一可续传的部分。
3. `channel`（`extract` / `probe:<面试官>` / `answer:<追问编号>` / `verdict:<主张编号>` / `suggest:<主张编号>`）
   只是界面路由标签，**刻意不参与卡带指纹**（cassette.ts 的 `shapeOf` 只看 system / messages / temperature / maxTokens / json）。

## 理由

- 分片是「观感」，不是结论。5800 个分片写进日志会让回放变慢、日志变吵，
  而拼接出来的文本并不比 done 事件更可信（可能缺尾，而下游要靠它做结构校验与锚定）。
- 断线续传的语义必须落在阶段边界上：分片丢了只是少看几行字，重连后阶段事件仍能完整接上。
- channel 不参与指纹，意味着已经录好的 29 盘演示卡带不必重录；
  否则每加一个纯观感特性都要重烧全部素材，离线演示会变得极难维护。

## 代价

- 刷新页面后，正在写的那几行字会消失（顶部阶段时间线仍然完整，历史重放也仍然完整）。
- 分片与阶段事件共用一路 SSE，前端必须按 `event` 分流：web/src/state.ts 里是两条队列——
  主队列按播放节奏（即时 / 慢放 220 ms）推进事件，分片走独立的快队列（40 ms 3 片），
  否则慢放模式下一次追问的几十个分片会让画面落后几十秒。

## 备选

- **分片落库**：能逐字回放，但事件表会膨胀两个数量级，重放还要复原分片时序，收益远小于代价。
- **WebSocket 分双通道**：天然分离，但引入第二套协议与第二条连接，与「单端口 + SSE」的取舍（ADR-0003）冲突。
