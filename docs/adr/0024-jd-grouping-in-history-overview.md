# ADR-0024：历史仪表盘按岗位要求分组，身份用正文算不用标题认

- 状态：已采纳（2026-10-28，P12 之后的补充）
- 相关：决策 D64、发现 F82/F83、`packages/shared/src/overview.ts`、`packages/server/src/overview.ts`、ADR-0019

## 背景

历史仪表盘原本只有两条线：跨场次的结论，以及「**同一份简历**跑过几场」（`resumeGroups`）。
但「改完再跑一遍」的常见姿势不是顺着简历改，而是**顺着一个岗位反复试**：同一份 JD，简历改了若干版，
每一版都跑一场。这时用户想问的是「这个岗位我到底跑过几场、最近这几版怎么样」，
而按简历分组恰好把答案拆散了——每改一版简历，`resumeHash` 就换一个值，一组变三组。

数据面已经齐了：每场会话的 JD 正文在 `jd` 表里（`listJds`，ORDER BY ordinal）。
缺的只是「按同一份 JD 把场次归起来」。

## 决策

1. **分组的身份是正文指纹，不是标题。** `jdKeyOf(texts) = shortHash(stableStringify(texts.map(t => t.replace(/\s+/g, " ").trim())), 16)`：
   先按空白归一（粘贴时多带空行不算换岗位），再对**这一场对照过的全部 JD 正文**取指纹。
   标题只用来展示。反过来会正好拧着：改个标题就把一条时间线劈成两条，正文改一个字却还留在同一组。
2. **一场进它对照过的每一个 JD 组。** 多 JD 场次同时出现在多组里——「同一个岗位跑过几场」这个问题
   对每一份 JD 都成立，分组是**关系**不是归属（与 F37「配色最小单位是关系」同族）。
   按归属做，多 JD 场次必然丢掉一边。
3. **排序写死**：场次降序 → 最近一场时间降序 → `jdKey` 升序。同样的输入永远同样的顺序，
   否则同一份数据在两个读者那里会摆出两种样子（ADR-0019 同款纪律）。
4. **聚合留在 shared，服务端只读数。** `groupByJd` 是纯函数，`packages/server/src/overview.ts` 只负责
   `listJds` 与算 `jdKey`；判定分布仍然复用 `compare.ts` 的 `verdictCounts`、类别短板仍然复用 `shortfall.ts`。
   同一件事只有一个作者（F69）。
5. **界面只说一句话，不重画一份统计。** `sameJdNote` 只报「《岗位》最多跑过 N 场」这一个数字，
   数字来自接口，点测直接对账（161 → 162 项）。多写第二份统计，迟早与接口对不上。
6. **与「按简历分组」正交、并列显示**：一个回答「顺着简历改有没有变好」，一个回答「这个岗位试了几版」。
   两组都只在 >1 场时出现，一句话，不占版面。
7. **不落库。** 分组每次现算，能现算的坐标不存第二份（ADR-0013 / ADR-0022 同一取舍）。
   窗口仍取 `OVERVIEW_WINDOW = 200` 场，不因为多了一个分组就加维度。

## 取舍

- **不做「同一个岗位、不同人的对比」**：那是跨用户的事，超出本地单机的范围（隐私口径见 README）。
- **不给「这个岗位你进步了多少分」这种单一分数**：与 ADR-0019 同一条理由——趋势只画已判与站得住两根柱，
  不把多档判定压成一个数字。
- **标题不做唯一性处理**：两份不同的 JD 可以叫同一个名字，界面会显示两组同名。
  这是刻意的：名字是给人的，身份是正文算的，界面上看起来重复好过悄悄把两份合成一份。
- **超窗口的场次不进分组**：与仪表盘其余数字同一口径，分组不会偷偷多看几场。

## 代价

JD 正文只要动一个字（哪怕只是标点），就会变成新的一组，历史看起来「断了」。
这是选「身份=正文」的必然代价；换来的是一条判断：**同一份 JD 就是同一份 JD**，不会因为标题相同而认错，
也不会因为标题改了而认散。真要在两份近似 JD 之间挪动，用户看得见那是一次换岗位。
