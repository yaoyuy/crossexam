# ADR-0009：采纳改写从原文重算，接口只收主张 id

- 状态：已采纳
- 日期：2026-10-26
- 相关：ADR-0006（报告导出格式）、`packages/shared/src/revise.ts`、`packages/server/src/revisions.ts`、`packages/server/src/resume-export.ts`

## 背景

用户第 8 条要求（m04531）：「提出问题后，用户确认后应自动把简历做对应修改，并提供 PDF 或 DOC 导出」。

界面上的建议是「把这一段换成那一段」。最直接的实现是让前端把改前改后一起发回来，服务端做字符串替换。
这条路有三个问题：

1. **注入面**：接口一旦接受任意文本替换，任何人带着 sessionId 就能把任意内容写进简历，服务端无从判断这段文字该不该出现；
2. **叠加不可逆**：按顺序把 N 处替换套上去，「撤销」就需要反向操作，反向操作一旦有一点偏差就再也回不到原文；
3. **偏移会乱**：每替换一处，后面所有坐标都要平移；靠调用方自己算，早晚会算错（这也是 `movedSpans` 存在的理由）。

## 决策

1. **接口只收主张 id**：`POST /api/sessions/:id/revisions` 的 body 是 `{ claims: string[] }`，即**本次勾选的全部主张**（不是增量）。
   改前改后都从库里那条 `suggestion` 读——用户能决定的只是「采纳哪几条」，决定不了「改成什么」。
2. **每次都从原文重算**：采纳记录是一个**集合**，不是一串操作。`applyRevisions(原文, 所有勾选的建议)` 一次算完，
   所以「先采纳 C1 再采纳 C3」与「一次采纳 [C1, C3]」逐字节相同。撤销 = 清空集合重算，不需要反向操作。
3. **改不动要说出理由**：引文在原简历里锚不住（用户改过原文）、该主张没有建议、点名的 claimId 不存在，
   三类都进 `skipped` 并带一句中文原因，界面显示「勾了但没改成：…」。**宁可明说少改一处，也不静默跳过。**
4. **标记坐标按累计位移重算**：`movedSpans(applied)` 从已采纳的替换列表自己累加平移量，不接受调用方传入的原文。
   传原文进来只会多一个「两份原文不一致」的失败模式。
5. **简历与报告分开渲染**：新增 `resume-export.ts`，不复用 `report-html.ts`。报告是质询结论，简历是要发给 HR 的东西；
   混在一起会让简历带上满屏判定徽章。默认导出是干净的一版，`marks=1` 才标绿并附「本版改了什么（N 处）」。

## 后果

- 好处：写操作的范围被收窄到「库里已有的那几条建议」，注入面消失；撤销是幂等的；导出与预览必然一致（同一份 `RevisedView`）。
- 代价：用户想改一句建议之外的话，只能回去改简历原文再重跑一场。这是刻意的——这个产品的定位是「替你审」，不是「替你写」。
- 代价：服务端多存一份 `revised_resume`（原文仍在 `session.resumeText`，两份都可导出）。
