# ADR-0011：岗位模板库是数据，一键采用是幂等的服务端动作

- 状态：已采纳
- 日期：2026-10-27
- 相关：ADR-0008（自建面试官的产物是契约）、`packages/shared/src/templates.ts`、`packages/server/src/http/app.ts`、`docs/roadmap-v2.md`

## 背景

用户在 m07544 第 2 条说：「D1 行业模板库还是太少了」。这条要求的实际场景是：
一个不懂某个行业的评委（或者一位跨专业求职的学生）打开这个工具，面对空白的简历框与 JD 框，
既不知道该喂什么料，也不知道这个产品到底能问出什么。

模板要解决的就是这十秒钟：点一下，得到一份「有东西可问」的料。

这里有两个容易走偏的方向：

1. **把模板做成代码**：写死在界面里，加一条模板就要改组件、重新发版；
2. **把「采用」做成一个新建动作**：用户点两次就多出两位一模一样的面试官，库里堆满重复项，
   而面试官库是全局的（ADR-0008），堆起来的垃圾会在每一位后来的用户面前出现。

还有一条合规约束（AGENTS.md 第 8 节）：不做招聘平台爬虫。BOSS 直聘的 robots.txt 对 `User-agent: *` 写了 `Disallow: /*?*`，
而职位列表页全是带查询参数的 URL；加之用户协议禁止批量抓取。所以这 36 条模板的 JD 与示例简历**全部原创**。

## 决策

1. **模板是数据，不是代码**：数据放在 `packages/shared/src/templates/`（四个分片 + 一个合并出口 `templates.ts`），
   形状是 `JobTemplate`：`{ id, industry, title, jd, resume, hints, presets, custom }`。
   界面只读不写：`GET /api/templates` 把数据连同指纹一起发出去，前端不重复实现规则。
2. **一键采用是幂等的服务端动作**：`POST /api/templates/:id/apply`。模板自带的那位面试官，
   其 id 由 `customInterviewerId(custom.name, template.id)` **派生**而来——同一个模板永远得到同一个 id，
   于是点两次是「复用」而不是「新建」。返回里的 `created` 字段让界面能如实说明是哪一种。
   派生 id 而不是「查库里有没同名的」：同名判定会被用户改名打破，派生 id 不会。
3. **翻库不落库**：只有 apply 才写 `interviewer` 表。浏览一遍 36 条模板不该往库里塞几十位面试官——
   那会让「面试官库」这个全局空间变成垃圾桶。
4. **每条模板都必须留可追问的点**：示例简历刻意保留「下降明显」「参与抢救十余次」「深受学生喜爱」这类说法，
   同时带具体数字。否则一场质询全是「站得住」，恰好演示不出这个产品在干什么。
   这条由测试守住：每条简历必须命中一份模糊措辞表里至少一个词，且必须含数字。
5. **字数上下限进常量，由一处校验**：`TEMPLATE_LIMITS`（JD 180–260 字、示例简历 200–340 字、
   每条 2–3 条提示、正好 2 位推荐面试官）写在数据旁边，`templateProblems(list)` 是全库唯一的校验入口，
   测试既拿它验 36 条全过，也拿它验「注入一处毛病会被点名」。

## 后果

- 好处：加一个行业只改数据文件；「十秒得到一份有东西可问的料」这条体验有了可复现的证据（服务端测试 + 界面点测 + 截图）。
- 好处：幂等采用让面试官库不会被同一个模板污染，`created` 也让界面能说人话。
- 代价：模板里的文案改了，`templateDigest` 就变，涉及模板的断言与文档里的字数都要跟着改（同一类问题的处置规则见 findings F27）。
- 代价：36 条模板是把「行业覆盖面」做成了数据量，扩到 60 条只是写数据，但要重新跑一遍全量校验。
