# docs/screenshots —— 界面截图（由命令生成，不是手点的）

    npm run build && npm run shots

生成器是 [tools/ui-shots](../../tools/ui-shots/README.md)：真起服务、真起浏览器（系统 Edge/Chrome，走 CDP）、
按 `data-shot` 锚点走完一遍操作，顺便把控制台报错当失败。也就是说这批图随时可以重新生成，
而不是「上次截的图」——README、技术文档、演示视频封面都用它们。

17-adopt.png 拍的是真的点过「全部采纳 → 确认采纳」之后的界面：右栏不是预览，是服务端按集合重算出来的那一版，导出按钮拿到的就是它（txt 逐字一致，PDF 是同一份 HTML 经浏览器打印）。

18-templates.png 里的模板是**数据**不是写死的界面：36 条（12 个行业 × 3 个岗位）放在 `packages/shared/src/templates/`，浏览模板不写库，只有点下去才把模板自带的那位面试官装进全局面试官库——而且按模板 id 派生 id，同一个模板点两次是「复用」不是「新建」。这一张里的面试官就这么来的。

19-requirements.png 里的对照是回放模式跑出来的（一键示例自带一份 235 字的 JD，抽出 7 条要求）：追问的两处锚点都落在业务表里，
所以刷新页面、翻回历史会话，右栏仍然能聚焦到 JD 的那一段——点的是 JD 引文，跳的是 JD 原文，和简历引文用的是同一套聚焦机制。
20 / 21 / 22 / 23 这四张是「追问深化」的四个角度，拍的都是同一场回放：同一份判定换个角度读（按类别看短板）、
同一批面试官换个追问预算（三档强度，人设一字不动）、用户自己补一句真话（零宽插入，原文不动）、以及把材料反着用一遍（轮到你了，每句都必须锚回原文）。
它们的共同点是**不新增任何判定口径**——结论只从已有的主张、判定与追问里算出来，所以四栏的数字永远对得上。
25 / 26 这两张同样没让模型多判一次：成长档案只把相邻两版的主张连成轨迹（ADR-0021），一岗一版只做「留下 / 不留下」（ADR-0022），两个结论都能从原文、采纳记录与要求对照里推出来。

16-studio.png 里的「医护面试官」是用**本地规则**生成的（不联网、确定性），存下来的自定义面试官与五位预设共用同一套契约结构、
同一套渲染与指纹逻辑——这是「任何行业都能配自己的面试官」那条要求最直接的证据。

其中 04-live-output.png 与 05-thinking.png 是**回放模式**下拍的（`npm run shots` 为了零 Key 可复跑，一律用示例卡带）：
分片由回放端按 24 字软切生成，思考那一行来自合成脚本写在卡带里的 `reasoning` 字段。真实联网下同一栏由 SSE 的 `event: stream` 填充：
正文分片来自模型输出，思考分片来自思考模型的 `reasoning_content`——2026-10-26 实测一场 5814 片正文 / 2355 片思考 / 8 路 `verdict:*` 通道，且分片都不进事件表（见 docs/adr/0004、docs/adr/0005、findings F22）。

所有画面用的都是内置示例简历（合成素材），不含任何真实个人简历。
