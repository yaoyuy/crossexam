# tools/repro —— 干净目录复现预演

    npm run repro

把仓库当成评委第一次见到它的样子：**在一个干净的临时目录里** clone、安装、过门禁、起服务、跑完一场质询，
逐步计时，最后与 README 里「10 分钟极速复现」这条承诺比对。

## 为什么需要它

开发目录里躺着 `node_modules`、`.env`、构建产物和已种好的卡带——这些**恰好会掩盖最常见的复现失败**：
忘了提交某个文件、依赖只装在本地、命令必须在某个子目录里跑、卡带没进仓库。
在自己的机器上「我这儿能跑」不算证据，在干净目录里跑过才算。

这也是评分表里「过程可复现性与演进链路」25% 的直接证据：承诺要能被一条命令复核。

## 它做了什么

1. 确认上游仓库工作区是干净的（脏工作区复现出来的不是评委拿到的那份东西，直接拒绝；调试脚本本身可用 `--allow-dirty`）；
2. `git clone` 到系统临时目录；
3. `npm install`；
4. `npm run verify`（类型检查 + 测试 + 真进程冒烟 + 构建）；
5. 起服务（回放模式）→ 打健康检查 → 拉首页确认是构建好的界面 → 用示例简历建档 → 跑完一场质询 → 取统计与 Markdown 报告；
6. 逐步打印耗时，合计超过 600 秒就退出码 1；跑完删掉临时目录。

全程只读上游仓库，所有写入都在临时目录里。

## 参数

| 参数 | 作用 |
| --- | --- |
| `--repo <path>` | 被预演的仓库（默认本仓库） |
| `--dir <path>` | 指定临时目录 |
| `--keep` | 保留临时目录与现场，便于排查 |
| `--skip-install` | 跳过安装（调脚本时用） |
| `--allow-dirty` | 允许脏工作区（结论不作数，仅用于调试本脚本） |
| `--timeout-min <n>` | 单步超时（默认 15 分钟） |
| `--quiet` | 不转发子进程输出 |

端口默认 8795，可用 `CROSSEXAM_REPRO_PORT` 改（避免撞上正在开发的服务）。

## 基线（本机实测，2026-10-26）

| 步骤 | 耗时 |
| --- | --- |
| git clone | 7.6 s |
| npm install（116 个包） | 15.5 s |
| npm run verify | 13.8 s |
| 起服 + 跑完一场 + 下载报告 | 0.5 s |
| 合计 | 约 40 s |

耗时与机器、镜像源有关，量级才是重点：**没有需要编译的依赖，所以复现不会被本地工具链卡住**。
同一台机器上两次实测 clone 分别 2.8 s 与 7.6 s（磁盘缓存冷热差异），合计 35–40 s——
所以 README 里写的是量级（约 40 秒、上限 600 秒），不是某一秒的精确值。

## 踩过的坑

- Windows 上 `npm` 实际是 `npm.cmd`：Node 从 20.12 起不允许无 shell 地 spawn `.cmd`，
  而带 shell 又会触发 DEP0190（参数不转义）。最终改成「node + 本机自带的 npm-cli.js」，两边都不沾。
- 脚本自己也会被「上游脏工作区」挡住——这是设计，不是 bug；迭代脚本时用 `--allow-dirty`。
